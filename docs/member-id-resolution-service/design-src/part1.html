Member ID Resolution Service

A small Spring Boot REST service that takes the member ID Onyx received from a provider's EMR, verifies it against the Master Member Index (MMI), returns the ID exactly as stored and in the format the chosen UM vendor expects, and says whether coverage is active on the date of service.

Status draft v0.1 for review, no code yet Date 2026-10-03 Stack Java 17 · Spring Boot 3.5 · Gradle · STS-importable Sample vendors eviCore · Carelon · Optum · MHK (placeholders)

1Summary

Every UM vendor wants the member ID in its own shape. THP cards show 9 digits; our system of record stores 9 digits, three spaces and a two-digit suffix (14 characters); EMRs send anything in between; HPHC IDs start with HP. Today the mismatch is discovered at the vendor. This service moves the check to the front of the flow and answers one call from Onyx with four things: the ID as received, the ID as stored in MMI, the ID rendered for the vendor, and the coverage status on the date of service.

Four business answers (HTTP 200)

ACTIVE INACTIVE NOT_FOUND AMBIGUOUS
Onyx branches on one field, outcome.

Three Onyx branches

200: act on outcome. Any 4xx or 422: never retry, route by code. Any 5xx or no response: one retry-and-park ladder.

What it never does

Never guesses a suffix, never returns an ID MMI did not confirm, never sends names or DOB to MMI, never returns names or SSN, never caches, no database, no queue.

Shape of the code

One controller, one orchestrator, four pure domain components (parser, selector, coverage evaluator, formatter), one MMI client behind a retry and a circuit breaker. About 40 small classes.

The one thing to read if nothing else

A 9-digit THP card number identifies a policy, not a person. MMI may return the whole family or only the subscriber for it, and we do not yet know which. The service therefore treats a 9-digit input without the patient's date of birth as not confirmed: it answers AMBIGUOUS instead of picking someone. If Onyx sends the patient's date of birth (it has it from the EMR request), the same input resolves safely. Whether Onyx can send the DOB on every request is the first decision below, and it is load-bearing.

3Scope and non-goals

In scope (v1)

  • One endpoint, POST /api/v1/member-ids/resolve: validate the ID through MMI, return received / normalized / canonical / vendor-formatted IDs and the coverage status on one date of service.
  • Parsing of every variation named so far: 9, 11 and 14 characters, any separator, HPHC prefix, any case. Strict rejection of everything else.
  • One MMI call per request plus at most one retry; timeouts, circuit breaker, fast-fail 503.
  • Deterministic handling of 0 / 1 / many MMI records: dependents, converted THP↔HPHC members, duplicates, unrelated records.
  • Optional patient DOB used only to verify or pick among records MMI already returned.
  • Vendor → format mapping inside the service (YAML plus two enums), validated at startup.
  • Closed outcome and error vocabulary with HTTP status, stable code, retryable flag and the Onyx action for each.
  • Correlation between the Onyx transaction and MMI's requestId, metrics, alerts, health, PHI-safe logging, Spring profiles with the four MMI URLs.
  • In-process stub MMI for local runs in STS, same fixtures as the tests.

Non-goals

  • No demographic search of MMI. The ID is the only search key; the DOB never leaves the service.
  • No caching, persistence, audit database, batch or asynchronous mode. Onyx stores the full response with its transaction and is the system of record.
  • No degraded or best-effort answer when MMI is down (rationale in section 13).
  • No coverage over a date range, no benefit or PCP adjudication, no vendor transport.
  • No person-wide search: a patient who also holds another plan ID (dual coverage) is not looked up by the other ID.
  • No pass-through of names, SSN, MBI, PCP, group name or any demographic. Only identifiers and coverage facts leave the service.
  • No public vendor-list endpoint; the effective table is on the management port and in the startup log.

4How a request flows

Everything runs synchronously on the request thread. No executors, no async, no state between requests.

  1. Edge filters. Read or generate X-Correlation-Id, put it in the log context and the response header. Check X-Api-Key (constant-time compare) → 401.
  2. Deserialize with the strict mapper (unknown property, wrong JSON type, malformed JSON → 400). Body larger than 16 KB → 413.
  3. Validate everything in one pass: member ID shape, date of service format and window, DOB format and plausibility, vendor present and well-formed. All problems are returned together in error.details[]. No MMI call for an invalid request.
  4. Resolve the vendor by key or alias → 400 UNKNOWN_VENDOR.
  5. Parse the member ID into one of three shapes: THP_9, THP_11, HPHC (section 7).
  6. Build the MMI request: the normalized ID in both memberId and legacyMemberId, voidCoverageRecord = N, our clientId, clientType = INT, a fresh requestId. No DOS range, no demographics, no searchMode.
  7. Call MMI through the circuit breaker and the one-retry rule (section 13). Transport failures → 503; MMI rejections and unusable bodies → 502.
  8. Interpret the envelope with the message-classification table (section 8.4): not found, usable, or rejected.
  9. Normalize the records: keep memberId verbatim as the canonical value, parse it for matching, parse dates strictly, classify each coverage span as valid, void or unreadable.
  10. Select the candidate (section 9): relate every record to the input, drop unrelated ones, merge duplicates, group into persons, apply the DOB, choose the record that represents the patient on the date of service. Result: one record, or NOT_FOUND, AMBIGUOUS, IDENTITY_MISMATCH.
  11. Evaluate coverage on the selected person (section 10) → ACTIVE or INACTIVE with a reason, or 502 when an unreadable span could be the covering one.
  12. Format for the vendor (section 11) from the stored ID's parts, never from the input. NOT_SUPPORTED → 422.
  13. Respond, write one INFO line per request, increment memberid_resolve_total{outcome,vendor}.
Precedence rule

Coverage is evaluated before formatting, but a vendor that cannot take this member's company wins: an INACTIVE THP member sent to a vendor configured NOT_SUPPORTED for THP is 422 UNSUPPORTED_FOR_VENDOR, not 200 INACTIVE. The vendor cannot be used regardless of coverage.
