10Selecting the member

From the records MMI returned to the one that represents the patient on the date of service. MMI's record order is never a criterion, and nobody is ever picked "by default".

  1. Merge duplicates. Two records with the same company and the same stored ID (compared without whitespace, case-insensitively) become one, with their spans combined. A warning is logged.
  2. Link converted pairs. Records linked through legacyMemberId in either direction (A's legacy id is B's id, or the reverse, transitively) are one person with several records. This is how a THP↔HPHC conversion comes back from MMI's second pass.
  3. Apply the date of birth, when sent (an unusable one is a 400 on both operations, section 6.4). If at least one record carries a DOB, keep only persons with a matching DOB. None left → 422 DOB_MISMATCH, including when a single record came back (an EMR that appended 01 to a dependent's card number is caught here). If no record carries a DOB at all, continue unverified with a warning: a request with a DOB is never worse off than one without.
  4. Count persons. One → step 5. Several → AMBIGUOUS with one candidate per person (the record covering the date, else the most recent), sorted by ID; the message says whether a date of birth was applied and still did not separate them (twins) or none was sent, and what to resend.
  5. Pick the record within the person. One record: that one. Several (a converted member): the record whose coverage covers the date of service; if both do, the newer record (the one naming the other as its legacy id); if neither does, the record whose coverage ends last. Coverage is then evaluated over all of the person's spans, so a gap between the old and the new record is a gap, not "coverage ended". The vendor format follows the picked record's company: a member converted to HPHC gets the HPHC ID for a post-migration date and the THP ID for a pre-migration date.

TMP and SCO have no dependents, so a 9-character card number always yields one person and resolves directly; no DOB is needed. Only Together and HPHC commercial families can reach AMBIGUOUS.

11Coverage status

Evaluated on the selected record's readable, non-void spans. lineOfBusiness, restrictedData and groupId take no part in the decision.

  1. Covers: a span covers the date iff effDate ≤ date ≤ endDate, both inclusive; endDate null, blank or 12/31/9999 is open-ended.
  2. ACTIVE iff at least one span covers the date. The reported span is the covering span with the latest start (then the latest end).
  3. INACTIVE otherwise, with exactly one reason, said in message and in the log, not as a field: NO_COVERAGE_RECORDS (no readable, non-void spans), NOT_YET_EFFECTIVE (date before the earliest start), COVERAGE_ENDED (date after the latest end), COVERAGE_GAP (between spans).
  4. Calendar dates only, no time zones, and no upper limit on the date (feedback 20): the date judged is always the date sent. A future date against a record that ends before it is COVERAGE_ENDED (a record 01/01/2026 to 12/31/2026 is INACTIVE for any 2027 date); against an open-ended record (end blank or 12/31/9999) it is ACTIVE, because that is what the record says. A retro-termination that ended coverage after the date of service but before today is still ACTIVE on that date.
  5. Unreadable spans are skipped (bad date text, end before start) with a warning that names the record (masked) and the shape of the bad value. The remaining spans decide. If the member has unreadable spans and no readable one, the answer is 502 UNREADABLE_COVERAGE: a confident INACTIVE on data the service could not read would block care.

12Vendor mapping

Four format styles are code; the vendors are a YAML map in application.yaml. No table anywhere else. A vendor change is a YAML edit and a deployment; a new output shape is one enum constant, one switch case and one test row.

public enum VendorIdFormat {
    AS_STORED,     // exactly as MMI stores it            123456789   01
    COMPACT_11,    // 9 characters + suffix, no spaces        12345678901
    SPACED_14,     // 9 characters + 3 spaces + suffix        123456789   01
    SPLIT          // two fields: 9 characters and suffix     "123456789" + "01" (and the 11-character join)
}

A format is applied only when the stored ID has the TMP/SCO shape, 9 characters, one or more spaces, 2 digits (^(\d{9})\s+(\d{2})$). A continuous 11-character Public Plans ID or an HPHC ID does not match and is passed through verbatim for every vendor, so MHK's 14-character format can never turn 34567890101 into something else.

At startup the table is validated (keys ^[A-Z0-9_]{2,32}$, a format on every vendor, aliases unique across vendors) and printed, rendered against the sample stored ID 123456789 01, in the first lines of the log. An unknown enum value or a shared alias stops the application with a message naming the key.

The vendor map (section 6.6) is rendered from this same table: VendorRegistry.all(), sorted by code, one vendorMemberIds entry per key. A vendor added here appears in every vendor-map response from the next deployment, with no code change. The same shape rule applies to every entry: only a stored TMP/SCO id is reshaped; a Public Plans or HPHC id is the stored value on all of them.

14Running it: resilience, security boundary, PHI, logging

  • Resilience is timeouts and clear statuses, nothing more. Connect 2 s, read 5 s; a failure is a 503 or 502 within seconds; Onyx retries later. No retry, no circuit breaker, no bulkhead, no degraded mode: MMI is a core service, outages are short, and each of those mechanisms is code that must be tested, configured and explained to Onyx.
  • If this service is down, Onyx passes the EMR's member ID through to the vendor as received (owner's rule), whichever operation it was calling. Nothing to build here beyond keeping the service boring: stateless, two replicas, graceful shutdown.
  • Security is outside this code. Azure API Management in front of the service owns authentication, certificates and credentials. The service listens on plain HTTP 9090 inside the network and calls MMI over plain HTTP, as the MMI contract states. Actuator exposes only health and info. Swagger UI and the OpenAPI document are off in prod.
  • PHI minimisation. Request: member ID, date, optional DOB and the vendor (required on /resolve, optional and ignored on /vendor-map). Response: identifiers, line of business, the covering coverage period. Never: names, DOB, SSN, MBI, PCP, group names. SSN and names are not even declared on the MMI DTOs. Every request and MMI DTO overrides toString() to the masked form; the exception handler never echoes Jackson or validation messages. MMI's code and text are forwarded to Onyx: in sourceMessage on NOT_FOUND and in the messages of 400 MEMBER_LOOKUP_REJECTED, 503 HTTP_500 and 502 ERROR_MESSAGE; they are not written to the log at INFO.
  • Logging. One INFO line per request: operation (resolve or vendor-map), outcome, reason, vendor (ALL(5) on the vendor map), masked received and stored IDs, company, line of business, date, whether defaulted, record count, MMI request id, elapsed time. One INFO line per MMI call. Warnings with a searchable marker for data anomalies (UNREADABLE_SPAN, DUPLICATE_RECORDS_MERGED, COMPANY_INFERRED, DOB_UNAVAILABLE_ON_RECORDS, CONVERTED_OVERLAP, CORRELATION_ID_REPLACED, MMI_NOT_FOUND_WITH_MEMBERS when MMI answers 404 but still returns members, which are used; MMI_404_WITHOUT_ENVELOPE when MMI's 404 carries a body that is not MMI's envelope: still NOT_FOUND, but if every id comes back that way check mmi.base-url and mmi.path). The console pattern carries the correlation id. Payload logging for troubleshooting: with mmi.log-payloads: true the exact MMI request body and the raw response body (status, content type, elapsed time) are written to the log, unmasked, one line each. It is on in dev (the stub prints the same lines), fqa, pqa and pqa-lite, and off in prod: those bodies contain PHI. A test captures the log during every scenario and asserts no unmasked nine-digit run and no date of birth ever appears.
  • Correlation chain. Onyx transaction id → this service's lines → traceId → MMI's logs. No PHI needed to follow one transaction.
  • Health. /actuator/health with liveness and readiness groups; MMI is deliberately not part of readiness, so an MMI outage never scales this service to zero.

20Glossary

MMI
Master Member Index: Point32Health's enterprise member service. Internal only; the only thing this service calls.
THP / HPHC
The two heritage companies, Tufts Health Plan and Harvard Pilgrim Health Care. A converted member has one record in each, linked by legacyMemberId.
TMP / SCO
Tufts Medicare Preferred and Senior Care Options: THP Medicare membership. Cards print 9 characters; MMI stores 9 characters + 3 spaces + 01. No dependents.
Public Plans
THP's Together, Direct and SNP populations; 11-character continuous IDs; families with dependents.
Onyx
The integration platform that receives prior-authorization requests from provider EMRs and routes them to UM vendors. The only caller.
UM vendor
Utilization-management partner: eviCore, Evolent, Carelon, MHK, Optum; Onyx itself is also configured as a vendor (11 characters).
Stored ID
The member ID exactly as MMI holds it (memberId.stored).
For-vendor ID
The stored ID rendered in a vendor's format (memberId.forVendor on /resolve, vendorMemberIds[].memberId on the vendor map); the only value Onyx forwards.
Vendor map
The second operation, POST /api/v1/member-ids/vendor-map: the member id in every vendor's format at once, vendorMemberIds[], for when Onyx does not yet know the vendor.
MMI message
What MMI said in its messages[] when it had no member for the id, forwarded as sourceMessage { type, status, code, text } on NOT_FOUND. MMI's 404 is such an answer, not a failure.
Received ID
The member ID as Onyx sent it, surrounding whitespace removed (memberId.received); exactly the value sent to MMI.
Span
One coverage period on a record; readable and non-void spans decide the flag.
Date of service (DOS)
The calendar date coverage is evaluated on: always the date Onyx sent, whatever year it is in; today only when Onyx sends none.
Worklist
A UM intake queue where a person resolves what the automation could not.
