Digits 1–9 are the core (policy ID, "subscriber id" in MMI terms). Suffix 01 is the subscriber; 02, 03… are dependents. The three spaces are literal characters in the stored value.

7.2 Normalization steps

  1. Reject null. Keep the verbatim value as memberId.received.
  2. Trim leading and trailing whitespace, including tabs, NBSP (U+00A0) and full-width space (U+3000). Empty → MEMBER_ID_MISSING; more than 40 characters → MEMBER_ID_TOO_LONG.
  3. Classify every character of the trimmed value: ASCII digit; ASCII letter; separator (any Unicode whitespace or space character, any dash punctuation such as -, en dash, non-breaking hyphen, plus _ . /); anything else → MEMBER_ID_ILLEGAL_CHARACTERS (the detail lists the offending code points, never the ID).
  4. Build compact: drop every separator, upper-case letters with Locale.ROOT. Separators are tolerated anywhere and never interpreted; deleting them cannot change a digit, and MMI verifies the result.
  5. Match compact against the shape table. No match → MEMBER_ID_UNRECOGNIZED_SHAPE.

IDs are strings end to end; leading zeros are significant. A numeric JSON value is rejected before it gets here (WRONG_JSON_TYPE), which also catches an upstream system that dropped leading zeros.

8.2 Dates

  • Onyx → service: DateTimeFormatter.ISO_LOCAL_DATE, ResolverStyle.STRICT.
  • MMI → service: MM/dd/uuuu STRICT (uuuu, not yyyy: strict resolution with yyyy fails without an era). 12/31/9999 and a null or blank endDate both mean open-ended (LocalDate.MAX internally, rendered null). The spec documents the 9999 default for HPHC only; THP's convention is Q7, and both are handled.
  • Service → Onyx: ISO yyyy-MM-dd.
  • An unparseable effDate or endDate, or endDate < effDate, makes the span unreadable (section 10). No guessing of other sentinels: FQA will show any THP convention immediately.

8.3 What we read from the response

The MMI DTOs declare only the fields the service uses and ignore everything else, so names, SSN, gender, PCP, group name, MBI and agency numbers are discarded during deserialization and cannot be logged or serialized by accident:

envelope
clientId, clientType, requestId, messages[]{messageType, statusCode, messageCode, message}, members[]
member
memberId, subscriberMemberId, memberDob (parsed only when the request carried a DOB, or for duplicate detection), legacyMemberId, company, lineOfBusiness, restrictedData, migrationEffectiveDate, coverage[]
coverage span
effDate, endDate, groupId, voidFlag

Scalar coercion is off on the shared ObjectMapper: a voidFlag that arrives as a JSON boolean, or a memberId that arrives as a number, is a 502 UNPARSEABLE_BODY rather than a silently wrong value. company is optional in the spec: when absent it is inferred from the ID shape (HP… → HPHC, 9 digits + suffix → THP) with a WARN; when present but contradicting the shape, the record is unusable (502 UNKNOWN_COMPANY if selected).

8.4 Interpreting the envelope: precedence table

MMI's exact codes for "no match", "invalid request" and "internal error" are unknown until FQA. Three lists hold them (mmi.not-found-http-statuses, mmi.not-found-message-codes, mmi.error-message-types), empty until filled from FQA evidence. The default when the lists cannot decide is to fail closed: an MMI partial outage must park and replay, never become a terminal "member not found".

8.5 Two guards against answering from the wrong place

  • Host matches profile. Each profile carries mmi.expected-host-pattern (for prod: ^mastermemberindexserviceapp-spring-boot-prod\.apps\.prodocp\.). Startup fails, naming profile and host, when mmi.base-url does not match. An emergency override edits the pattern property; there is no bypass boolean. This stops a PROD pod from quietly answering from the FQA index after a copy-paste or a mis-mounted ConfigMap.
  • Stub only in local. The in-process stub MMI client is created only when mmi.stub.enabled is true and the local or test profile is active; any other profile with the flag set fails startup. The startup report and /actuator/info show mmi.client: STUB | REST.

9Candidate selection: from MMI records to one person

Inputs: the MMI records R, the parsed input P, the optional DOB H, the date of service. Output: exactly one selected record, or NOT_FOUND, AMBIGUOUS or IDENTITY_MISMATCH. Steps run in order; each is unit-testable on fixture record sets. The order in which MMI returns records is never a criterion.

S0 — structural

Records with a blank memberId are dropped (WARN, metric). If R was non-empty and nothing remains → 502 NO_MEMBER_ID. If R is empty → 200 NOT_FOUND / NO_MMI_RECORDS.

Each record's memberId is parsed into a canonical form for matching after trimming (including NBSP) and upper-casing: THP ^(\d{9})\s*(\d{2})$ → core and suffix; HPHC ^HP\d+$. The verbatim stored value is what the response returns as memberId.canonical; the parsed parts are what the vendor format is rendered from, so a stored trailing space never reaches a vendor. A record whose ID does not parse is marked unparseable; it cannot be related to anything.

S1 — relatedness as a closure

ClassCondition
DIRECTrecord memberId equals P (THP_11: same core and suffix; HPHC: same id). 12345678901 and 123456789 01 compare equal.
FAMILYP is THP_9 and the record's THP core equals P.core (any suffix).
LEGACYrecord legacyMemberId equals P (or its core equals P.core for THP_9), or the record is linked to an already-admitted record in either direction (B.legacyMemberId == A.memberId, or A.legacyMemberId == B.memberId). Repeated until nothing new is admitted, at most 5 hops.
UNRELATEDnone of the above after the closure.

The closure matters in the common case, not only for exotic chains: when the input is the new HPHC ID, the old THP record carries no legacyMemberId (only the new record names the old one), so a one-directional comparison would drop the record that covers a pre-migration date of service.

UNRELATED records are dropped, counted, logged WARN (masked; a distinct marker when the dropped record was active on the DOS, which hints at an unlinked conversion), and never re-admitted. If nothing related remains → 200 NOT_FOUND / NO_RELATED_RECORD, or NO_RECORD_WITH_SUFFIX when P is THP_11 and records for the same core exist but none has this suffix. If nothing is related and at least one record had an unparseable ID → 502 CANONICAL_ID_UNPARSEABLE instead: stored-form drift must surface as a contract error, not as a NOT_FOUND spike.

S2 — duplicates

Group related records by (company, canonical id). Within a group, merge into one record when the memberDob values are present and equal, or all absent with identical span sets (a span is identical when effDate, endDate, groupId and voidFlag match after parsing). Otherwise → 200 AMBIGUOUS / DUPLICATE_RECORDS with an ERROR log: two different people, or two different coverage histories, under one ID is a data-quality incident worth surfacing, never something to resolve by taking the first row.

S3 — persons

A person is one THP (core, suffix) or one HPHC id, plus every record linked to it through legacyMemberId in either direction. A converted THP↔HPHC pair is one person with two records.

S4 — DOB verification and disambiguation (whenever a DOB was sent, including when one record came back)

  • Keep the persons that have at least one record whose memberDob equals the DOB.
  • Zero left → 422 IDENTITY_MISMATCH / DOB_MISMATCH. This catches the dominant 9-digit failure mode (MMI returned only the subscriber while the patient is a dependent) and the EMR that appended 01 to a dependent's card number.
  • One left → continue with identityVerified: true; selection.method = DOB when more than one person existed before the filter.
  • Several left (twins, same-DOB dependents) → 200 AMBIGUOUS / DOB_NOT_DISCRIMINATING.
  • memberDob absent on every related record → the DOB cannot be checked; continue on the no-DOB path with identityVerified: false and a WARN marker. A request with a DOB is never worse off than the same request without one.
  • memberDob present but unparseable on every related record → 502 DOB_UNPARSEABLE (contract drift, not an identity review).

S5 — how many persons

  • Several persons and no usable DOB → 200 AMBIGUOUS / MULTIPLE_PERSONS, one candidate per person (the record covering the DOS, else the most recent), sorted by company then id, capped at 10 with candidatesTruncated.
  • Exactly one person, input THP_9, no usable DOB → 200 AMBIGUOUS / PERSON_NOT_CONFIRMED with that one candidate. A 9-digit card number is not evidence of which family member, and we do not yet know whether a one-record answer means a one-person policy or "MMI only returns the subscriber". The single policy property member-id.thp9-single-record: AMBIGUOUS | ACCEPT defaults to AMBIGUOUS and is set to ACCEPT only after FQA proves a 9-digit search returns every suffix (18.4).
  • Exactly one person otherwise (THP_11 or HPHC direct hit, or a DOB-confirmed person) → S6.

Explicitly not done: defaulting to suffix 01, or to "the only active member".

S6 — one person, which record (converted pairs)

"New record" is the one whose legacyMemberId names the other's memberId; the migration date is migrationEffectiveDate from whichever record carries it (if both carry different dates, the new record's wins with a WARN). Coverage on the DOS is evaluated for each record of the person (section 10).

Evaluated on the selected person's records (coverage is per company; S6 chose the record whose company owns the DOS). migrationEffectiveDate, lineOfBusiness, restrictedData and groupId are reported but take no part in the decision.

10.2 Rules

  1. Covers: a VALID span covers the DOS iff effDate ≤ DOS ≤ endDate, both inclusive (a span ending on the DOS is still active that day; inclusive end to be confirmed, Q7).
  2. ACTIVE iff at least one VALID span covers the DOS. coverage.reason = COVERED. The reported span is the covering span with the latest effDate; tie → latest end (open-ended sorts last). More than one covering span → WARN + metric, not surfaced.
  3. Unreadable-span guard: if no VALID span of the selected person covers the DOS and any record of that person has an UNREADABLE span → 502 MMI_RESPONSE_INVALID / UNREADABLE_SPAN. An unreadable span may be the covering one, and a false INACTIVE blocks care; refusing is the only answer that is never wrong. ACTIVE proven by a VALID span is still returned, with unreadableSpanCount so the data problem stays visible. For candidates[] the same situation renders coverageOnDateOfService: UNKNOWN rather than a 502.
  4. INACTIVE otherwise, with exactly one reason, chosen in this order:
    ReasonConditionExtra fields
    NO_COVERAGE_RECORDSno VALID spans (array absent, empty, or all void)
    NOT_YET_EFFECTIVEDOS before the earliest effDatenextEffectiveDate

11Vendor mapping

Format styles are code: two small enums with a render method and a unit test each. Vendors are data: one YAML map. Adding or changing a vendor is a YAML edit; a brand-new output shape is one enum constant plus one test row. Two enums make "a THP style applied to an HPHC record" impossible by type.

enum ThpIdFormat {               // input: core (9 digits) and suffix (2 digits) parsed from the stored id
  CORE_SUFFIX_11,                // "12345678901"
  CORE_SPACES_SUFFIX_14,         // "123456789   01"   (as stored)
  NOT_SUPPORTED;                 // vendor does not take THP members → 422 UNSUPPORTED_FOR_VENDOR
  abstract String render(String core, String suffix);
}
enum HphcIdFormat {              // input: the stored id, e.g. "HP123456789"
  AS_STORED,
  NOT_SUPPORTED;
  abstract String render(String canonical);
}
record VendorConfig(String displayName, List<String> aliases, ThpIdFormat thpFormat, HphcIdFormat hphcFormat) {}

A lossy 9-digit style and a digits-only HPHC style are deliberately absent until a real vendor needs them; each would be one constant.

11.2 Startup validation (the application refuses to start, naming the offending key)

  1. member-id.vendors non-empty; each key matches ^[A-Z0-9_]{2,32}$ after upper-casing.
  2. Both formats present and valid enum names (the binding error lists the valid values).
  3. Aliases unique across vendors, case-insensitive, and never equal to another vendor's key.
  4. vendors-source is not SAMPLE in pqa, pqa-lite and prod.
  5. Self-test: every configured style renders 123456789/01 and HP123456789; one INFO table vendor | THP sample | HPHC sample is logged so the effective mapping is visible in the first 20 log lines of every environment, and the same table is exposed at /actuator/info.

11.3 How to add a vendor

Add a block under member-id.vendors (key, optional aliases, two formats); deploy or roll the ConfigMap; check the startup table or /actuator/info. If the vendor needs a shape no constant produces, add one enum constant with its render and one test row. No other code changes.
