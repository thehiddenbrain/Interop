Member ID Resolution Service

A small Spring Boot REST service that takes the member ID Onyx received from a provider's EMR, verifies it against the Master Member Index (MMI), returns the ID exactly as stored and in the format the chosen UM vendor expects, and says whether coverage is active on the date of service.

Status draft v0.1 for review, no code yet Date 2026-10-03 Stack Java 17 · Spring Boot 3.5 · Gradle · STS-importable Sample vendors eviCore · Carelon · Optum · MHK (placeholders)

1Summary

Every UM vendor wants the member ID in its own shape. THP cards show 9 digits; our system of record stores 9 digits, three spaces and a two-digit suffix (14 characters); EMRs send anything in between; HPHC IDs start with HP. Today the mismatch is discovered at the vendor. This service moves the check to the front of the flow and answers one call from Onyx with four things: the ID as received, the ID as stored in MMI, the ID rendered for the vendor, and the coverage status on the date of service.

Four business answers (HTTP 200)

ACTIVE INACTIVE NOT_FOUND AMBIGUOUS
Onyx branches on one field, outcome.

Three Onyx branches

200: act on outcome. Any 4xx or 422: never retry, route by code. Any 5xx or no response: one retry-and-park ladder.

What it never does

Never guesses a suffix, never returns an ID MMI did not confirm, never sends names or DOB to MMI, never returns names or SSN, never caches, no database, no queue.

Shape of the code

One controller, one orchestrator, four pure domain components (parser, selector, coverage evaluator, formatter), one MMI client behind a retry and a circuit breaker. About 40 small classes.

The one thing to read if nothing else

A 9-digit THP card number identifies a policy, not a person. MMI may return the whole family or only the subscriber for it, and we do not yet know which. The service therefore treats a 9-digit input without the patient's date of birth as not confirmed: it answers AMBIGUOUS instead of picking someone. If Onyx sends the patient's date of birth (it has it from the EMR request), the same input resolves safely. Whether Onyx can send the DOB on every request is the first decision below, and it is load-bearing.

3Scope and non-goals

In scope (v1)

  • One endpoint, POST /api/v1/member-ids/resolve: validate the ID through MMI, return received / normalized / canonical / vendor-formatted IDs and the coverage status on one date of service.
  • Parsing of every variation named so far: 9, 11 and 14 characters, any separator, HPHC prefix, any case. Strict rejection of everything else.
  • One MMI call per request plus at most one retry; timeouts, circuit breaker, fast-fail 503.
  • Deterministic handling of 0 / 1 / many MMI records: dependents, converted THP↔HPHC members, duplicates, unrelated records.
  • Optional patient DOB used only to verify or pick among records MMI already returned.
  • Vendor → format mapping inside the service (YAML plus two enums), validated at startup.
  • Closed outcome and error vocabulary with HTTP status, stable code, retryable flag and the Onyx action for each.
  • Correlation between the Onyx transaction and MMI's requestId, metrics, alerts, health, PHI-safe logging, Spring profiles with the four MMI URLs.
  • In-process stub MMI for local runs in STS, same fixtures as the tests.

Non-goals

  • No demographic search of MMI. The ID is the only search key; the DOB never leaves the service.
  • No caching, persistence, audit database, batch or asynchronous mode. Onyx stores the full response with its transaction and is the system of record.
  • No degraded or best-effort answer when MMI is down (rationale in section 13).
  • No coverage over a date range, no benefit or PCP adjudication, no vendor transport.
  • No person-wide search: a patient who also holds another plan ID (dual coverage) is not looked up by the other ID.
  • No pass-through of names, SSN, MBI, PCP, group name or any demographic. Only identifiers and coverage facts leave the service.
  • No public vendor-list endpoint; the effective table is on the management port and in the startup log.

4How a request flows

Everything runs synchronously on the request thread. No executors, no async, no state between requests.

  1. Edge filters. Read or generate X-Correlation-Id, put it in the log context and the response header. Check X-Api-Key (constant-time compare) → 401.
  2. Deserialize with the strict mapper (unknown property, wrong JSON type, malformed JSON → 400). Body larger than 16 KB → 413.
  3. Validate everything in one pass: member ID shape, date of service format and window, DOB format and plausibility, vendor present and well-formed. All problems are returned together in error.details[]. No MMI call for an invalid request.
  4. Resolve the vendor by key or alias → 400 UNKNOWN_VENDOR.
  5. Parse the member ID into one of three shapes: THP_9, THP_11, HPHC (section 7).
  6. Build the MMI request: the normalized ID in both memberId and legacyMemberId, voidCoverageRecord = N, our clientId, clientType = INT, a fresh requestId. No DOS range, no demographics, no searchMode.
  7. Call MMI through the circuit breaker and the one-retry rule (section 13). Transport failures → 503; MMI rejections and unusable bodies → 502.
  8. Interpret the envelope with the message-classification table (section 8.4): not found, usable, or rejected.
  9. Normalize the records: keep memberId verbatim as the canonical value, parse it for matching, parse dates strictly, classify each coverage span as valid, void or unreadable.
  10. Select the candidate (section 9): relate every record to the input, drop unrelated ones, merge duplicates, group into persons, apply the DOB, choose the record that represents the patient on the date of service. Result: one record, or NOT_FOUND, AMBIGUOUS, IDENTITY_MISMATCH.
  11. Evaluate coverage on the selected person (section 10) → ACTIVE or INACTIVE with a reason, or 502 when an unreadable span could be the covering one.
  12. Format for the vendor (section 11) from the stored ID's parts, never from the input. NOT_SUPPORTED → 422.
  13. Respond, write one INFO line per request, increment memberid_resolve_total{outcome,vendor}.
Precedence rule

Coverage is evaluated before formatting, but a vendor that cannot take this member's company wins: an INACTIVE THP member sent to a vendor configured NOT_SUPPORTED for THP is 422 UNSUPPORTED_FOR_VENDOR, not 200 INACTIVE. The vendor cannot be used regardless of coverage.

5API contract for Onyx

POST /api/v1/member-ids/resolve, Content-Type: application/json. POST rather than GET because the member ID is PHI and must not appear in URLs or access logs. The operation is a pure read and idempotent: Onyx may replay any request verbatim with no side effects. The service always answers JSON regardless of the Accept header.

6What Onyx does with each answer, and when we are down

Three branches, in order: (1) HTTP 200 → act on outcome; (2) any 4xx or 422, with or without a JSON body → never retry, route by code; (3) any 5xx, or no usable HTTP response → one retry-and-park ladder. retryable is true on every 5xx and Retry-After gives the first wait, so the flag and the status class can never disagree.

7.2 Normalization steps

  1. Reject null. Keep the verbatim value as memberId.received.
  2. Trim leading and trailing whitespace, including tabs, NBSP (U+00A0) and full-width space (U+3000). Empty → MEMBER_ID_MISSING; more than 40 characters → MEMBER_ID_TOO_LONG.
  3. Classify every character of the trimmed value: ASCII digit; ASCII letter; separator (any Unicode whitespace or space character, any dash punctuation such as -, en dash, non-breaking hyphen, plus _ . /); anything else → MEMBER_ID_ILLEGAL_CHARACTERS (the detail lists the offending code points, never the ID).

  5. Match compact against the shape table. No match → MEMBER_ID_UNRECOGNIZED_SHAPE.

IDs are strings end to end; leading zeros are significant. A numeric JSON value is rejected before it gets here (WRONG_JSON_TYPE), which also catches an upstream system that dropped leading zeros.

9Candidate selection: from MMI records to one person

Inputs: the MMI records R, the parsed input P, the optional DOB H, the date of service. Output: exactly one selected record, or NOT_FOUND, AMBIGUOUS or IDENTITY_MISMATCH. Steps run in order; each is unit-testable on fixture record sets. The order in which MMI returns records is never a criterion.

S0 — structural

Records with a blank memberId are dropped (WARN, metric). If R was non-empty and nothing remains → 502 NO_MEMBER_ID. If R is empty → 200 NOT_FOUND / NO_MMI_RECORDS.

Each record's memberId is parsed into a canonical form for matching after trimming (including NBSP) and upper-casing: THP ^(\d{9})\s*(\d{2})$ → core and suffix; HPHC ^HP\d+$. The verbatim stored value is what the response returns as memberId.canonical; the parsed parts are what the vendor format is rendered from, so a stored trailing space never reaches a vendor. A record whose ID does not parse is marked unparseable; it cannot be related to anything.

S1 — relatedness as a closure

ClassCondition
DIRECTrecord memberId equals P (THP_11: same core and suffix; HPHC: same id). 12345678901 and 123456789 01 compare equal.
FAMILYP is THP_9 and the record's THP core equals P.core (any suffix).
LEGACYrecord legacyMemberId equals P (or its core equals P.core for THP_9), or the record is linked to an already-admitted record in either direction (B.legacyMemberId == A.memberId, or A.legacyMemberId == B.memberId). Repeated until nothing new is admitted, at most 5 hops.

The closure matters in the common case, not only for exotic chains: when the input is the new HPHC ID, the old THP record carries no legacyMemberId (only the new record names the old one), so a one-directional comparison would drop the record that covers a pre-migration date of service.

UNRELATED records are dropped, counted, logged WARN (masked; a distinct marker when the dropped record was active on the DOS, which hints at an unlinked conversion), and never re-admitted. If nothing related remains → 200 NOT_FOUND / NO_RELATED_RECORD, or NO_RECORD_WITH_SUFFIX when P is THP_11 and records for the same core exist but none has this suffix. If nothing is related and at least one record had an unparseable ID → 502 CANONICAL_ID_UNPARSEABLE instead: stored-form drift must surface as a contract error, not as a NOT_FOUND spike.

S2 — duplicates

Group related records by (company, canonical id). Within a group, merge into one record when the memberDob values are present and equal, or all absent with identical span sets (a span is identical when effDate, endDate, groupId and voidFlag match after parsing). Otherwise → 200 AMBIGUOUS / DUPLICATE_RECORDS with an ERROR log: two different people, or two different coverage histories, under one ID is a data-quality incident worth surfacing, never something to resolve by taking the first row.

S3 — persons

A person is one THP (core, suffix) or one HPHC id, plus every record linked to it through legacyMemberId in either direction. A converted THP↔HPHC pair is one person with two records.

S4 — DOB verification and disambiguation (whenever a DOB was sent, including when one record came back)

  • Keep the persons that have at least one record whose memberDob equals the DOB.
  • Zero left → 422 IDENTITY_MISMATCH / DOB_MISMATCH. This catches the dominant 9-digit failure mode (MMI returned only the subscriber while the patient is a dependent) and the EMR that appended 01 to a dependent's card number.
  • One left → continue with identityVerified: true; selection.method = DOB when more than one person existed before the filter.
  • Several left (twins, same-DOB dependents) → 200 AMBIGUOUS / DOB_NOT_DISCRIMINATING.
  • memberDob absent on every related record → the DOB cannot be checked; continue on the no-DOB path with identityVerified: false and a WARN marker. A request with a DOB is never worse off than the same request without one.
  • memberDob present but unparseable on every related record → 502 DOB_UNPARSEABLE (contract drift, not an identity review).

S5 — how many persons

  • Several persons and no usable DOB → 200 AMBIGUOUS / MULTIPLE_PERSONS, one candidate per person (the record covering the DOS, else the most recent), sorted by company then id, capped at 10 with candidatesTruncated.
  • Exactly one person, input THP_9, no usable DOB → 200 AMBIGUOUS / PERSON_NOT_CONFIRMED with that one candidate. A 9-digit card number is not evidence of which family member, and we do not yet know whether a one-record answer means a one-person policy or "MMI only returns the subscriber". The single policy property member-id.thp9-single-record: AMBIGUOUS | ACCEPT defaults to AMBIGUOUS and is set to ACCEPT only after FQA proves a 9-digit search returns every suffix (18.4).
  • Exactly one person otherwise (THP_11 or HPHC direct hit, or a DOB-confirmed person) → S6.

Explicitly not done: defaulting to suffix 01, or to "the only active member".

Add a block under member-id.vendors (key, optional aliases, two formats); deploy or roll the ConfigMap; check the startup table or /actuator/info. If the vendor needs a shape no constant produces, add one enum constant with its render and one test row. No other code changes.

13.3 Degraded, best-effort answers: not in v1

When MMI is down the service could, in principle, reformat a syntactically complete 11- or 14-character input without verification. It will not. That reformatted ID is exactly the guess this service exists to remove: for a 9-digit card ID the suffix is unknowable; for the others the ID may be converted, terminated or mistyped; and coverage status cannot be produced at all. MMI outages are measured in minutes (to be confirmed with 12 months of incident history, Q12), and Onyx's park-and-replay covers them without a second code path that would need its own tests, alerts and Onyx handling. If the owner later wants it, it is an additive verification: UNVERIFIED field behind an explicit request flag, never the default. The 503 body deliberately carries no partial member data; Onyx already holds the received ID and vendor in its own transaction.

14Security and PHI

  • Network placement. MMI is reachable only inside the Point32Health OpenShift estate over plain HTTP, as its spec states, and this service is assumed to run in the same cluster (platform question Q20). A NetworkPolicy allowing this namespace egress to MMI, and ingress only from the Onyx namespace (ClusterIP service and no route if Onyx is in-cluster; otherwise a route with insecureEdgeTerminationPolicy: None and an IP allow-list), is an infrastructure ticket. The MMI base URL is configuration, never derived from request data.
  • Onyx → service. TLS terminated at the OpenShift route with the enterprise certificate; the pod listens on HTTP 8080. X-Api-Key checked with MessageDigest.isEqual; keys come from a Secret as MEMBERID_API_KEYS, comma-separated, so two keys are valid during a rotation and no coordinated cut-over with Onyx is needed. One distinct key per environment. Enabled in every profile but local; startup fails when the list is empty. The key filter covers every path on 8080, API docs included; /api-docs and Swagger UI are off in prod.
  • PHI minimisation on the wire. Request: member ID, DOS, vendor, optional DOB. Response: identifiers, company, suffix/relationship, coverage dates, group id, line of business. Never: names, DOB (including on candidates and on IDENTITY_MISMATCH), SSN, MBI, PCP, group name, agency numbers.
  • SSN and names never enter the process model. They are not declared on the MMI DTOs and are discarded during deserialization. memberDob is held in memory only for the DOB check and duplicate detection.
  • Logging. Member IDs masked everywhere (*****6789 01, HP*****6789); DOB never logged; every request and MMI DTO overrides toString() to the masked form so a framework DEBUG line cannot print PHI; the exception handler never logs or returns ex.getMessage() for Jackson or validation failures (fixed detail codes and the JSON path instead); MMI message text at DEBUG only; raw MMI bodies only when mmi.log-bodies is true and the local profile is active (checked in code). Framework loggers are pinned to INFO in non-local profiles and the startup report WARNs when any PHI-adjacent logger is below INFO. A capturing-appender test asserts no log line contains an unmasked nine-digit run or a date of birth.
  • Error bodies never contain MMI message text or stack traces (server.error.include-message/stacktrace: never; all errors go through one handler, including Tomcat-level 4xx, so every response carries the envelope). The received vendor string is never echoed.
  • Input bounds. Strict deserialization, a 16 KB Content-Length cap answered with the 413 envelope, Jackson stream constraints (string 8 KB, nesting 16) on the one shared mapper, and vendor looked up in a fixed map and never used in a path.
  • Actuator on management port 8081, not routed outside the namespace: health, info, prometheus only. env, configprops, heapdump and threaddump stay off; the JVM runs with -XX:+ExitOnOutOfMemoryError and no heap dumps, since a dump would hold MMI responses.
  • Risk acceptance. Plain HTTP to MMI is inherited from the MMI contract; FQA tries the https variant of each route first, and if it is not served the interim acceptance is recorded here with the owner's name.
  • Audit. Onyx stores the full response body with its transaction and is the system of record for the decision. The service's one INFO line per request (correlation id, DOS, outcome, reason, masked canonical and vendorFormatted, selection method, MMI request ids) is enough to corroborate it; the log index needs one year of retention with access limited to the support group (infrastructure ticket), or the chain Onyx id → service log → MMI requestId breaks at the default 30–90 days.

21Glossary

MMI
Master Member Index: Point32Health's enterprise member service, Elasticsearch behind a Spring Boot API on OpenShift. Returns demographics and coverage spans for THP and HPHC. Internal only.
THP / HPHC
The two heritage companies, Tufts Health Plan and Harvard Pilgrim Health Care. A member record belongs to one; a converted member has one record in each.
Onyx
The integration platform that receives prior-authorization requests from provider EMRs and routes them to the right UM vendor. The only caller of this service.
UM vendor
Utilization-management partner that adjudicates prior authorizations: eviCore, Carelon, Optum, MHK (MedHOK) in the samples.
Core / suffix
A THP ID's first nine digits (the policy or subscriber number) and its two-digit member suffix (01 subscriber, 02+ dependents).
THP_9 / THP_11 / HPHC
The three input shapes the parser recognises: 9 digits, 9 digits plus suffix, HP plus digits.
Canonical
The member ID exactly as MMI stores it (THP: 14 characters with three spaces; HPHC: HP plus digits).
Vendor-formatted
The canonical ID rendered in the chosen vendor's style. The only value Onyx forwards to a vendor.
Converted member
A member moved between THP and HPHC. MMI links the two records through legacyMemberId and migrationEffectiveDate.
Person
One THP (core, suffix) or one HPHC id plus every record linked to it by conversion. The unit the service selects.
DOS
Date of service: the date on which coverage is evaluated. One calendar date per call.
Span
One coverage period (effDate–endDate) on a record; valid, void or unreadable.
Park / replay
Onyx holding a transaction in a retry store and re-sending it on a schedule, as opposed to a worklist, where a human acts.
Worklist
