WHAT THE SERVICE DOES AFTER THE MERGE
- The MMI search body carries dosStartDate (MM/dd/yyyy): the date of service, or today when the caller
  sent none, or the first day of a period. No dosEndDate.
- Once MMI has identified the member (ACTIVE or INACTIVE only), one call to the member information
  service: POST {member-info.base-url}/members with
    { "memberIds": [<resolved id as stored>], "dos": "MM/dd/yyyy", "returnCoverageList": true }
- lineOfBusiness comes from the coverage record (coverageRecords, not memberPlan) whose planStartDate and
  planEndDate include the date of service (both ends inclusive, no end = open, void records skipped):
    SCO            businessTypeIndicator SH and a planCode containing SCO (checked first)
    D-SNP          sourceSystemId 2064 and productCode DMA
    MA-TOGETHER    subsidiary THPPMA, sourceSystemId 2026, productCode PL or GT
    RI-TOGETHER    subsidiary THPPRI and sourceSystemId 2048
    MA-QHP         subsidiary THPPMA, sourceSystemId 2026, productCode NS or SB
  No covering record or no rule match: MMI's lineOfBusiness is kept (logged as LOB_NOT_DERIVED).
- A failure of that call fails the whole answer:
    unreachable, timeout, 5xx/429/408   503 MEMBER_PLAN_UNAVAILABLE, Retry-After: 10
    any other status (404 excepted)     502 MEMBER_PLAN_ERROR
    empty, unreadable or null body      502 MEMBER_PLAN_INVALID_RESPONSE
    404                                 not an error: no records
  Each carries MMI's request id as traceId. No response text names the member information service
  ("the member plan lookup").
- Open-ended coverage ends 12/31/3999: read as open from MMI, returned as coverage.endDate 3999-12-31,
  and as 39991231 at the end of coverageId.

STEP 5  The resolution (ResolutionService)
  reference: service/ResolutionService.java (method lineOfBusiness, and the use of lob in resolve and logOutcome)
  a) Inject MemberInfoClient memberInfo and LineOfBusinessDeriver lineOfBusiness.
  b) Add:
       /** The identified member's line of business: from the coverage record on the date of service, else MMI's. */
       private Mono<Optional<String>> lineOfBusiness(Resolved r, LocalDate dateOfService, String correlationId) {
           return memberInfo.lookup(r.storedMemberId(), dateOfService, correlationId)
                   .onErrorMap(MemberInfoException.class, e -> e.withTraceId(r.mmiRequestId()))
                   .map(info -> Optional.ofNullable(lineOfBusiness.derive(r.storedMemberId(), r.record().lineOfBusiness(),
                           info.coverageRecordsFor(r.storedMemberId()), dateOfService)));
       }
     Optional, not a bare String: MMI's lineOfBusiness can be null, and a null inside map() is an error in Reactor.
  c) In resolve, once the member is resolved (adapt the names to your reactive chain):
       Mono<Optional<String>> lob = r.record() == null
               ? Mono.just(Optional.empty())                          // NOT_FOUND / AMBIGUOUS: no call, no lineOfBusiness
               : lineOfBusiness(r, v.dateOfService(), correlationId);
       return lob.map(l -> /* build the response with l.orElse(null) as lineOfBusiness */);
     The response's lineOfBusiness and the "resolution ... lob=" log line take this value, not
     r.record().lineOfBusiness().
  d) Keep the call out of the MMI-failure paths: a 400/422/502/503 from MMI never reaches it.
