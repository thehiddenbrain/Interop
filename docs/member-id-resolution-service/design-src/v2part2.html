6API contract for Onyx

6.1 Operations and headers

Two operations, both POST with Content-Type: application/json: /api/v1/member-ids/resolve (sections 6.2 to 6.5, the id for one vendor) and /api/v1/member-ids/vendor-map (section 6.6, the id in every vendor's format). POST because the member ID is PHI and must not appear in URLs or access logs; both operations are pure reads and may be repeated. The service always answers JSON whatever Accept header is sent, and always sets Cache-Control: no-store. The headers below apply to both.

HeaderDirectionRule
X-Correlation-IdinOnyx transaction id, 1–64 characters of [A-Za-z0-9._:-], opaque. Missing or invalid → a UUID is generated (and a warning logged with the rejected length).
X-Correlation-IdoutEcho or generated value; also in the body as correlationId.
Retry-After: 10outOn 503 only.

6.2 Request (/resolve)

6.4 Errors (HTTP 4xx / 5xx)

One shape: { "error": { "code", "message", "details": [ { "field", "code", "message" } ] }, "correlationId", "mmiRequestId" }. mmiRequestId is present whenever MMI was called, on a 422 too, so identity review has the trace id. The same envelope serves both operations, but not the same codes: /vendor-map is lenient, and the only 400s of its own validation are MEMBER_ID_MISSING and a body that is not JSON for the operation (MALFORMED_JSON, or WRONG_JSON_TYPE when the body or a field has the wrong JSON type, for example an array where text is expected). The date codes, the vendor codes (VENDOR_MISSING, VENDOR_INVALID, UNKNOWN_VENDOR) and UNKNOWN_PROPERTY come only from /resolve. MMI's own 400 is forwarded as 400 MMI_BAD_REQUEST on both operations.

6.6 Vendor map: POST /api/v1/member-ids/vendor-map

Onyx does not always know which vendor will receive the authorization when it checks the member id. The vendor map is the same lookup without needing a vendor: one MMI call, the same selection and the same coverage decision, and the stored id rendered in every configured vendor's format instead of one. It is lenient: only the member id is required; a vendor or any unknown property is accepted and ignored, so Onyx may send its /resolve payload as is; an unusable date is ignored, not rejected, and named in ignoredFields. Onyx keeps the list with its transaction and takes the entry for the vendor once it knows it.

Request

FieldRequiredRules
memberIdyesAs in 6.2: presence only, sent to MMI exactly as typed with surrounding whitespace removed. Missing or blank is the one validation error of this operation: 400 INVALID_REQUEST / MEMBER_ID_MISSING, MMI not called.
dateOfServicenoyyyy-MM-dd within the window of 6.2. Omitted or blank: today, dateOfServiceDefaulted: true. Not a real date, or outside the window: ignored, today is evaluated, dateOfServiceDefaulted is true and "dateOfService" is listed in ignoredFields. Never a 400.
vendornoAccepted and ignored: the answer is always for every vendor. Lets Onyx send the /resolve payload unchanged. The value is never echoed or logged.
patient.dateOfBirthnoA real yyyy-MM-dd date, not in the future and not more than 125 years ago, is used as in 6.2 to verify or pick among the records MMI returned; one that matches no record is still 422 DOB_MISMATCH. Not a real date, or implausible: ignored, takes no part in the selection, and "patient.dateOfBirth" is listed in ignoredFields. Never sent to MMI, never logged, never echoed.
any other property–Ignored, at the top level and inside patient alike; not an error and not listed in ignoredFields.

The only 400s of this operation are a missing or blank memberId (MEMBER_ID_MISSING) and a body that is not JSON for the operation (MALFORMED_JSON; WRONG_JSON_TYPE when the body or a field has the wrong JSON type, for example "patient": "x"). Neither reaches MMI. Everything else is answered. The one other 400 comes from MMI itself: its 400 is forwarded as MMI_BAD_REQUEST on both operations (6.4).

7What Onyx does with each answer

Which operation: /resolve when Onyx already knows the vendor; /vendor-map when it does not, in which case Onyx keeps vendorMemberIds[] with the transaction and takes the entry for the vendor once it is known. One MMI call either way, and the rows below apply to both: the vendor map carries the same outcome, coverage, ambiguity and candidates. Onyx may send the same payload to both: on /vendor-map the vendor and any property the operation does not need are ignored, and an unusable date is ignored and named in ignoredFields rather than rejected. When ignoredFields is present the answer is complete and usable; the field tells Onyx support which request field was sent in a shape the service could not use.

8Member ID: passed through to MMI as typed

What arrives in memberId is not this service's business. It is checked for presence only (missing or blank → 400 MEMBER_ID_MISSING) and sent to MMI exactly as the EMR typed it, with only surrounding whitespace removed, in both memberId and legacyMemberId. No separator stripping, no upper-casing, no length cap, no classification. The owner's reasoning: EMRs send 9, 10, 11, 14, 20 or 40 characters, hyphens, whatever; if MMI can find the member it will, so a shape rule here can only reject real ids (a real PQA id was rejected by the earlier parser) and is MMI's job, not this service's.

9.1 The request

  "clientId": "MBRIDSVC", "clientType": "INT", "requestId": "MBRIDSVC-1791086059251-93795" }
  • memberId and legacyMemberId both carry the id exactly as received: the MMI spec's advice to improve the hit rate, and exactly the converted-member case (an EMR still holding the pre-conversion ID).
  • No dosStartDate/dosEndDate: the full history is evaluated locally so INACTIVE can say why and show the nearest dates. No searchMode. No demographics ever.
  • requestId follows MMI's convention, new per call, logged with the correlation id and returned to Onyx as mmiRequestId.
  • Timeouts: connect 2 s, read 5 s (mmi.connect-timeout / mmi.read-timeout). No retry: MMI is a core service that answers quickly in normal operation; a 5-second answer is a problem worth surfacing, and Onyx retries later on a 503.

9.2 What we read

The MMI DTOs declare only memberId, subscriberMemberId, memberDob, legacyMemberId, company, lineOfBusiness, restrictedData, migrationEffectiveDate and coverage[]{effDate, endDate, groupId, voidFlag}, plus the envelope's messages[]. Names, SSN, gender, PCP, group name, MBI and agency numbers are discarded during deserialization and cannot be logged or returned by accident. Dates are MM/dd/yyyy, parsed strictly; endDate null, blank or 12/31/9999 means open-ended.

9.3 Interpreting the answer

MMI's contract has four answers: 200 success, 404 member not found, 400 bad request, 500 internal error. This service maps them one to one: on 200 the records decide the outcome; MMI's 404 is 200 NOT_FOUND; MMI's 400 is 400 MMI_BAD_REQUEST with MMI's text; MMI's 500 is 503 MMI_UNAVAILABLE. Only an unknown route of this service is a 404 from this service. The mapping is fixed in RestMmiClient and ResolutionService; nothing about it is configurable. MMI's first message is returned to Onyx as mmiMessage on NOT_FOUND, and MMI's message code and text are appended to the 400 and 503 messages when MMI sent them. Any status outside the four is not MMI speaking but a gateway, proxy or container, and the answer says so.

9.4 The stub

For developer runs and tests an in-process stub answers from mmi-stub/members.json with MMI's documented behaviour: exact match, 9-character match returning the family, legacy-id match and the second pass through legacyMemberId. It receives the id exactly as the service got it from Onyx and matches its fixtures ignoring separators and case (anything that is not a letter or digit is ignored), which is the leniency the owner describes for the real MMI; lastSearched() hands tests the id as the stub received it, so they can prove nothing was reshaped on the way. An id that matches no fixture is answered like the real MMI: HTTP 404 with messages: [ { "messageType": "ERROR", "statusCode": "404", "messageCode": "MEMBER_NOT_FOUND", "message": "No member found for the given id (stub)" } ] and no members, so a dev-profile NOT_FOUND carries that mmiMessage, and the stub's payload log line prints status=404. Reserved ids (recognised by the first 9 characters of that compacted key) simulate the rest of MMI's contract and the data faults: 500500500 MMI's 500 → 503 HTTP_500 (message MMI reported an internal error: INTERNAL_ERROR search failed (stub)); 503503503 → 503 READ_TIMEOUT; 400400400 MMI's 400 → 400 MMI_BAD_REQUEST / HTTP_400 (message MMI rejected the request as a bad request: INVALID_REQUEST memberId could not be processed (stub)); 888888888 → 502 ERROR_MESSAGE (ES_TIMEOUT, text search backend timed out (stub)); 202202202 → 502 UNPARSEABLE_BODY; 887777777 → 200 with a warning (an error message beside a member); 886666666 → 502 NO_MEMBER_ID; 880000000 → 502 UNREADABLE_COVERAGE. In Postman the stub's "today" is the real date. Two guards keep canned answers out of PQA and PROD: the stub refuses to start with any explicitly active profile other than dev or test, and it refuses to start inside a Kubernetes/OpenShift pod at all (KUBERNETES_SERVICE_HOST). Because the default profile is dev (so STS runs with one click), every deployment must set SPRING_PROFILES_ACTIVE; a pod that forgets it fails at startup instead of answering from fixtures.
