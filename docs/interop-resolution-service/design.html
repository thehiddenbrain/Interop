Interop Resolution Service

The home for Onyx's interop lookups. First capability, and this document's subject: member ID resolution for prior authorization. Payer ID and payer organization name lookups are planned to join it (owner, 2026-10-05); until then it was the Member ID Resolution Service.

A small, stateless Spring Boot service for Onyx. It takes the member ID exactly as the provider's EMR supplied it, verifies it with the Master Member Index (MMI), returns the ID as stored and in the format each UM vendor expects, all vendors in one answer, and says with one flag whether coverage is active on the date of service, or throughout a period of service.

1Summary

Every UM vendor stores our member ID in its own shape. A THP Medicare (TMP) or SCO card prints 9 characters; our systems store those 9 characters, three spaces and the suffix 01 (14 characters); eviCore, Evolent and Carelon keep 11 characters without the spaces, MHK keeps all 14, Optum keeps only the 9 characters printed on the card. EMRs type whatever is on the card. Today the mismatch surfaces at the vendor. This service moves the check to the front of the flow: one call from Onyx, one call to MMI, and back come the ID as received, the ID as stored, the ID in every vendor's format, the coverage flag and an id for the coverage period. One operation, POST /v1/interop/resolve, gives every vendor's format at once, so one call serves a prior authorization whose codes go to several vendors.

Four business answers (HTTP 200)

ACTIVE INACTIVE NOT_FOUND AMBIGUOUS
Onyx branches on outcome; coverage.active is the yes/no flag; message says the answer in one sentence.

Three Onyx branches

200: act on outcome. 400 or 422: never retry, route by code. 502, 503 or no response: retry later; if this service is down, pass the EMR's ID through.

Deliberately plain

No database, no cache, no queue, no retry or circuit-breaker machinery, no security envelope (Azure APIM owns that). About 50 small classes.

Delivered

Gradle project importable into STS, built like your other services (Spring Boot 4.0.7, Gradle 9.5, JDK 17 to 25), in-process MMI stub for developer runs, run scripts, README, Postman collection with tests on every request.

What changed since v0.1, in one paragraph

TMP and SCO members have no dependents, so a 9-character card number resolves directly; the "not confirmed" rule is gone. AMBIGUOUS applies only to populations with dependents (HPHC commercial, Together) when a 9-character ID returns several people and no date of birth settles it. The response is lean: stored replaces "canonical", a boolean coverage.active is the flag, and the legacy, migration, restricted and trace fields are gone. A missing date of service defaults to today and says so. Vendor formats live in application.yaml only (Evolent added, Optum as the 9-character core). Retry and circuit-breaker logic, the API key, the ConfigMap override and the host guard were removed: MMI is reliable, security is external, and a format change is a config edit plus a deploy.

4Scope and non-goals

In scope

  • One operation, POST /v1/interop/resolve: the member behind the id, the coverage flag for the date or period of service, and the id in every configured vendor's format, from one MMI call.
  • The member id is sent to MMI exactly as the EMR typed it, whatever its length, separators or case; this service checks only that one was sent.
  • One MMI call per request; TMP/SCO resolve from any form; dependents handled through the DOB or AMBIGUOUS with candidates; converted THP↔HPHC members handled through MMI's legacy link.
  • Coverage flag for the date of service, or for a period of service from dateOfService to dateOfServiceEnd (today when omitted), with the continuous coverage period; why an inactive member is not covered is said in the one-sentence message.
  • Vendor formats in application.yaml; a change is a config edit and a deploy.
  • Clear error envelope, masked logging, correlation id, in-process MMI stub for developer runs and tests (profile-guarded and refusing to run inside a pod), profiles with the four MMI URLs.

Non-goals

  • No demographic search of MMI; the ID is the only search key and the DOB never leaves the service.
  • No database, cache, queue, audit store, batch or asynchronous mode.
  • No retry, circuit breaker or degraded mode around MMI (owner: MMI is a core service and is restored quickly when it fails).
  • No authentication, tokens or certificates in this code; the Azure API Management layer in front of it owns security.
  • No pass-through of names, SSN, MBI, PCP, group names, legacy IDs or migration dates. Identifiers and coverage facts only.
  • No coverage over several unrelated dates in one call: one date, or one continuous period of service, per call.

5How a request flows

Synchronous, on the request thread, no state between requests. Steps 5 to 8 are the core of ResolutionService (resolveMember); step 9 renders the stored id for every vendor.

  1. Correlation. Read X-Correlation-Id (or generate a UUID); it goes into every log line, the X-Correlation-Id response header and the body of error responses.
  2. Read the JSON. Malformed JSON or a wrong JSON type is a 400. An unknown property, a vendor included, is ignored: the request type is declared @JsonIgnoreProperties(ignoreUnknown = true).
  3. Validate in one pass. Member ID present (the only check on it); date of service (a real yyyy-MM-dd date, not more than 10 years back, no upper limit; default to today only when omitted), end of a period of service, date of birth (format, plausibility); a sent date is always the date judged, never replaced by today (feedback 20). Every problem is returned together as one 400. No MMI call for an invalid request.
  4. Call MMI once with the member id exactly as received, surrounding whitespace removed (section 8), in both memberId and legacyMemberId, voidCoverageRecord = N, our clientId, a fresh requestId (section 9).
  5. Interpret the answer (section 9.3). MMI's HTTP 404 means "no member for this id": 200 NOT_FOUND, and what MMI said goes into sourceMessage. A 200 with no members is NOT_FOUND too, unless it carries an error-typed message (for example ES_TIMEOUT), which is a 502 forwarding MMI's code and text. MMI's 400 has already become a 400 MEMBER_LOOKUP_REJECTED and its 500 a 503 MEMBER_LOOKUP_UNAVAILABLE in the client, both carrying MMI's code and text. Otherwise map each record, keeping only readable, non-void coverage spans. A member with unreadable spans and no readable one is a 502, never a confident INACTIVE.
  6. Select the member (section 10): merge duplicates, join converted pairs, apply the DOB, one person or AMBIGUOUS.
  7. Evaluate coverage on the date of service, or on every day of the period of service (section 11).
  8. Format the stored ID (section 12), never the input, for every configured vendor: one vendorMemberIds entry per vendor, sorted by code.
  9. Respond with the outcome and its one-sentence message (on NOT_FOUND also sourceMessage), and write one INFO line with masked IDs, outcome, timings and the MMI request id.

6API contract for Onyx

6.1 Operation and headers

One operation, POST /v1/interop/resolve with Content-Type: application/json (owner feedback 29 and 30). It finds the member behind the id the EMR typed, says whether coverage is active on the date of service or on every day of a period of service, and returns the id as stored and in every configured vendor's format, so one call serves a prior authorization whose codes go to several vendors. The earlier /api/v1/member-ids/resolve, /api/v1/member-ids/vendor-map and /api/v1/members/resolution are gone and answer 404 ROUTE_NOT_FOUND. POST because the member ID is PHI and must not appear in URLs or access logs; the operation is a pure read and may be repeated. The service always answers JSON whatever Accept header is sent, and always sets Cache-Control: no-store.

Anything in the request the operation does not need, a vendor included, is ignored; a date that cannot be used is a 400, because the answer is always about the date that was sent.

The MMI DTOs declare only memberId, subscriberMemberId, memberDob, legacyMemberId, company, lineOfBusiness, restrictedData, migrationEffectiveDate and coverage[]{effDate, endDate, groupId, voidFlag}, plus the envelope's messages[]. Names, SSN, gender, PCP, group name, MBI and agency numbers are discarded during deserialization and cannot be logged or returned by accident. Dates are MM/dd/yyyy, parsed strictly; endDate null, blank or 12/31/9999 means open-ended.

9.3 Interpreting the answer

MMI's contract has four answers: 200 success, 404 member not found, 400 bad request, 500 internal error. This service maps them one to one: on 200 the records decide the outcome; MMI's 404 is 200 NOT_FOUND; MMI's 400 is 400 MEMBER_LOOKUP_REJECTED with MMI's text; MMI's 500 is 503 MEMBER_LOOKUP_UNAVAILABLE. Only an unknown route of this service is a 404 from this service. The mapping is fixed in RestMmiClient and ResolutionService; nothing about it is configurable. MMI's first message is returned to Onyx as sourceMessage on NOT_FOUND, and MMI's message code and text are appended to the 400 and 503 messages when MMI sent them. Any status outside the four is not MMI speaking but a gateway, proxy or container, and the answer says so.

10Selecting the member

From the records MMI returned to the one that represents the patient on the date of service. MMI's record order is never a criterion, and nobody is ever picked "by default".

  1. Merge duplicates. Two records with the same company and the same stored ID (compared without whitespace, case-insensitively) become one, with their spans combined. A warning is logged.
  2. Link converted pairs. Records linked through legacyMemberId in either direction (A's legacy id is B's id, or the reverse, transitively) are one person with several records. This is how a THP↔HPHC conversion comes back from MMI's second pass.
  3. Apply the date of birth, when sent (an unusable one is a 400, section 6.4). If at least one record carries a DOB, keep only persons with a matching DOB. None left → 422 DOB_MISMATCH, including when a single record came back (an EMR that appended 01 to a dependent's card number is caught here). If no record carries a DOB at all, continue unverified with a warning: a request with a DOB is never worse off than one without.
  4. Count persons. One → step 5. Several → AMBIGUOUS with one candidate per person (the record covering the date, else the most recent), sorted by ID; the message says whether a date of birth was applied and still did not separate them (twins) or none was sent, and what to resend.
  5. Pick the record within the person. One record: that one. Several (a converted member): the record whose coverage covers the date of service; if both do, the newer record (the one naming the other as its legacy id); if neither does, the record whose coverage ends last. Coverage is then evaluated over all of the person's spans, so a gap between the old and the new record is a gap, not "coverage ended". The vendor format follows the picked record's company: a member converted to HPHC gets the HPHC ID for a post-migration date and the THP ID for a pre-migration date.

TMP and SCO have no dependents, so a 9-character card number always yields one person and resolves directly; no DOB is needed. Only Together and HPHC commercial families can reach AMBIGUOUS.

11Coverage status

Evaluated on the selected person's readable, non-void spans, for the date of service or for every day of the period of service (feedback 21). lineOfBusiness, restrictedData and groupId take no part in the decision.

  1. Covers: a span covers the date iff effDate ≤ date ≤ endDate, both inclusive; endDate null, blank or 12/31/9999 is open-ended.
  2. Continuous periods: spans that overlap or touch (one starts the day after the other ends, as plan-year records do) are one coverage period, from the earliest start to the latest end (open when any of them is open). A hole of one day is a gap.
  3. ACTIVE iff one continuous period covers every day from the first to the last date of service. The reported span is that period.
  4. INACTIVE otherwise, with exactly one reason, said in message and in the log, not as a field: NO_COVERAGE_RECORDS (no readable, non-void spans), NOT_YET_EFFECTIVE (date before the earliest start), COVERAGE_ENDED (date after the latest end), COVERAGE_GAP (between periods), COVERAGE_ENDS_WITHIN_PERIOD (a period covers the first day of the period of service but ends before the last; that period is reported so intake sees how far coverage goes).
  5. Calendar dates only, no time zones, and no upper limit on the date (feedback 20): the date judged is always the date sent. A future date against a record that ends before it is COVERAGE_ENDED (a record 01/01/2026 to 12/31/2026 is INACTIVE for any 2027 date); against an open-ended record (end blank or 12/31/9999) it is ACTIVE, because that is what the record says. A retro-termination that ended coverage after the date of service but before today is still ACTIVE on that date.
  6. Unreadable spans are skipped (bad date text, end before start) with a warning that names the record (masked) and the shape of the bad value. The remaining spans decide. If the member has unreadable spans and no readable one, the answer is 502 UNREADABLE_COVERAGE: a confident INACTIVE on data the service could not read would block care.

Four format styles are code; the vendors are a YAML map in application.yaml. No table anywhere else. A vendor change is a YAML edit and a deployment; a new output shape is one enum constant, one switch case and one test row.

14Running it: resilience, security boundary, PHI, logging

  • Resilience is timeouts and clear statuses, nothing more. Connect 2 s, read 5 s; a failure is a 503 or 502 within seconds; Onyx retries later. No retry, no circuit breaker, no bulkhead, no degraded mode: MMI is a core service, outages are short, and each of those mechanisms is code that must be tested, configured and explained to Onyx.
  • If this service is down, Onyx passes the EMR's member ID through to the vendor as received (owner's rule), whichever operation it was calling. Nothing to build here beyond keeping the service boring: stateless, two replicas, graceful shutdown.
  • Security is outside this code. Azure API Management in front of the service owns authentication, certificates and credentials. The service listens on plain HTTP 9090 inside the network and calls MMI over plain HTTP, as the MMI contract states. Actuator exposes only health and info. Swagger UI and the OpenAPI document are off in PRD.
  • PHI minimisation. Request: member ID, date or period of service, optional DOB. Response: identifiers, line of business, the covering coverage period. Never: names, DOB, SSN, MBI, PCP, group names. SSN and names are not even declared on the MMI DTOs. Every request and MMI DTO overrides toString() to the masked form; the exception handler never echoes Jackson or validation messages. MMI's code and text are forwarded to Onyx: in sourceMessage on NOT_FOUND and in the messages of 400 MEMBER_LOOKUP_REJECTED, 503 HTTP_500 and 502 ERROR_MESSAGE; they are not written to the log at INFO.
  • Logging. One INFO line per request: resolution, outcome, reason, masked received and stored IDs, company, line of business, date, whether defaulted, record count, MMI request id, elapsed time. One INFO line per MMI call. Warnings with a searchable marker for data anomalies (UNREADABLE_SPAN, DUPLICATE_RECORDS_MERGED, COMPANY_INFERRED, DOB_UNAVAILABLE_ON_RECORDS, CONVERTED_OVERLAP, CORRELATION_ID_REPLACED, MMI_NOT_FOUND_WITH_MEMBERS when MMI answers 404 but still returns members, which are used; MMI_404_WITHOUT_ENVELOPE when MMI's 404 carries a body that is not MMI's envelope: still NOT_FOUND, but if every id comes back that way check mmi.base-url and mmi.path). The console pattern carries the correlation id. Payload logging for troubleshooting: with mmi.log-payloads: true the exact MMI request body and the raw response body (status, content type, elapsed time) are written to the log, unmasked, one line each. It is on in DEV (the stub prints the same lines), FQA, PQA and PQA-LITE, and off in PRD: those bodies contain PHI. A test captures the log during every scenario and asserts no unmasked nine-digit run and no date of birth ever appears.
  • Correlation chain. Onyx transaction id → this service's lines → traceId → MMI's logs. No PHI needed to follow one transaction.
  • Health. /actuator/health with liveness and readiness groups; MMI is deliberately not part of readiness, so an MMI outage never scales this service to zero.

20Glossary

MMI
Master Member Index: Point32Health's enterprise member service. Internal only; the only thing this service calls.
THP / HPHC
The two heritage companies, Tufts Health Plan and Harvard Pilgrim Health Care. A converted member has one record in each, linked by legacyMemberId.
TMP / SCO
Tufts Medicare Preferred and Senior Care Options: THP Medicare membership. Cards print 9 characters; MMI stores 9 characters + 3 spaces + 01. No dependents.
Public Plans
THP's Together, Direct and SNP populations; 11-character continuous IDs; families with dependents.
Onyx
The integration platform that receives prior-authorization requests from provider EMRs and routes them to UM vendors. The only caller.
UM vendor
Utilization-management partner: eviCore, Evolent, Carelon, MHK, Optum (which stores the 9-character core only); Onyx itself is also configured as a vendor (11 characters).
Resolved ID
The member ID the lookup resolved to, exactly as MMI holds it for the member it settled on (memberId.resolved; called stored until feedback 31).
Vendor id
The stored ID rendered in one vendor's format, vendorMemberIds[].memberId; the only value Onyx forwards to that vendor.
Coverage id
coverage.coverageId: MEMBER_ID + EFF_DATE + END_DATE run together, letters and digits only, dates yyyyMMdd; names the period behind an answer.
Member resolution
The operation, POST /v1/interop/resolve: the member behind the id, the coverage on the date of service and the id in every vendor's format at once. Called the vendor map until feedback 29.
MMI message
What MMI said in its messages[] when it had no member for the id, forwarded as sourceMessage { type, status, code, text } on NOT_FOUND. MMI's 404 is such an answer, not a failure.
Received ID
The member ID as Onyx sent it, surrounding whitespace removed (memberId.received); exactly the value sent to MMI.
Span
One coverage record's period. Readable, non-void spans that overlap or touch are joined into one continuous period; those periods decide the flag, and the one covering the date of service is reported as coverage.effectiveDate and coverage.endDate.
Date of service (DOS)
The calendar date coverage is evaluated on: always the date Onyx sent, whatever year it is in; today only when Onyx sends none. With dateOfServiceEnd, every day from the first to the last.
Worklist
A UM intake queue where a person resolves what the automation could not.
