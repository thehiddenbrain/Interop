Member ID Resolution Service

A small, stateless Spring Boot service for Onyx. It takes the member ID exactly as the provider's EMR supplied it, verifies it with the Master Member Index (MMI), returns the ID as stored and in the format the chosen UM vendor expects, and says with one flag whether coverage is active on the date of service.

Status v0.2, code delivered (member-id-resolution-service/), reviewed, 124 tests green, Postman collection verified Date 2026-10-03 Stack Spring Boot 4.0.7 · Java 17+ · Gradle 9.5 · port 9090 (the EPA Workbench build shape) Only integration MMI

1Summary

Every UM vendor stores our member ID in its own shape. A THP Medicare (TMP) or SCO card prints 9 digits; our systems store those 9 digits, three spaces and the suffix 01 (14 characters); eviCore, Evolent and Carelon keep 11 characters without the spaces, MHK keeps all 14, Optum receives the 9 digits and the suffix as two separate fields. EMRs type whatever is on the card. Today the mismatch surfaces at the vendor. This service moves the check to the front of the flow: one call from Onyx, one call to MMI, and back come the ID as received, the ID as stored, the ID in the vendor's format and the coverage flag.

Four business answers (HTTP 200)

ACTIVE INACTIVE NOT_FOUND AMBIGUOUS
Onyx branches on outcome; coverage.active is the yes/no flag.

Three Onyx branches

200: act on outcome. 400 or 422: never retry, route by code. 502, 503 or no response: retry later; if this service is down, pass the EMR's ID through.

Deliberately plain

No database, no cache, no queue, no retry or circuit-breaker machinery, no security envelope (Azure APIM owns that). About 45 small classes.

Delivered

Gradle project importable into STS, built like your other services (Spring Boot 4.0.7, Gradle 9.5, JDK 17 to 25), in-process MMI stub for developer runs, run scripts, README, Postman collection (45 requests, all assertions green against the running service).

What changed since v0.1, in one paragraph

TMP and SCO members have no dependents, so a 9-digit card number resolves directly; the "not confirmed" rule is gone. AMBIGUOUS applies only to populations with dependents (HPHC commercial, Together) when a 9-digit ID returns several people and no date of birth settles it. The response is lean: stored replaces "canonical", a boolean coverage.active is the flag, and the legacy, migration, restricted and trace fields are gone. A missing date of service defaults to today and says so. Vendor formats live in application.yaml only (Evolent added, Optum as two fields). Retry and circuit-breaker logic, the API key, the ConfigMap override and the host guard were removed: MMI is reliable, security is external, and a format change is a config edit plus a deploy.

4Scope and non-goals

In scope

  • One endpoint, POST /api/v1/member-ids/resolve.
  • Every ID variation seen so far: 9, 11 and 14 characters, any separator, HP- with the card hyphen, any case.
  • One MMI call per request; TMP/SCO resolve from any form; dependents handled through the DOB or AMBIGUOUS with candidates; converted THP↔HPHC members handled through MMI's legacy link.
  • Coverage flag for the date of service (today when omitted), with the reason and the nearest span dates.
  • Vendor formats in application.yaml; a change is a config edit and a deploy.
  • Clear error envelope, masked logging, correlation id, in-process MMI stub for developer runs and tests (profile-guarded and refusing to run inside a pod), profiles with the four MMI URLs.

Non-goals

  • No demographic search of MMI; the ID is the only search key and the DOB never leaves the service.
  • No database, cache, queue, audit store, batch or asynchronous mode.
  • No retry, circuit breaker or degraded mode around MMI (owner: MMI is a core service and is restored quickly when it fails).
  • No authentication, tokens or certificates in this code; the Azure API Management layer in front of it owns security.
  • No pass-through of names, SSN, MBI, PCP, group names, legacy IDs or migration dates. Identifiers and coverage facts only.
  • No coverage over a date range; one date per call.

5How a request flows

Synchronous, on the request thread, no state between requests.

  1. Correlation. Read X-Correlation-Id (or generate a UUID); it goes into every log line, the response header and the body.
  2. Read the JSON strictly: an unknown property, a wrong JSON type or malformed JSON is a 400.
  3. Validate everything in one pass: member ID shape, date of service (format, window, default to today), date of birth (format, plausibility), vendor present and well-formed. Every problem is returned together. No MMI call for an invalid request.
  4. Look up the vendor by code or alias, case-insensitively → 400 UNKNOWN_VENDOR with the known codes.
  5. Normalise the member ID into one of three shapes (section 8).
  6. Call MMI once with the normalised ID in memberId and legacyMemberId, voidCoverageRecord = N, our clientId, a fresh requestId (section 9).
  7. Interpret the answer: no members → NOT_FOUND (or 502 if MMI reported an error); otherwise map each record, keeping only readable, non-void coverage spans. A member with unreadable spans and no readable one is a 502, never a confident INACTIVE.
  8. Select the member (section 10): merge duplicates, join converted pairs, apply the DOB, one person or AMBIGUOUS.
  9. Evaluate coverage on the date of service (section 11).
  10. Format the stored ID for the vendor (section 12), never the input.
  11. Respond and write one INFO line with masked IDs, outcome, vendor, timings and the MMI request id.

8.1 Steps

  1. Trim; empty → MEMBER_ID_MISSING; more than 40 characters → MEMBER_ID_TOO_LONG.
  2. Classify every character: digit, letter, separator (any whitespace, any dash including the en dash, _ . /), anything else → MEMBER_ID_ILLEGAL_CHARACTERS (the detail names the code points, never the ID).

  4. Match the shape table; no match → MEMBER_ID_UNRECOGNIZED_SHAPE (the message says "10 digits", never the value).

9MMI integration

9.1 The request

POST {mmi.base-url}/master/member/v1      (plain HTTP, no auth, as the MMI contract states for internal consumers)
Content-Type: application/json · Accept: application/json · X-Correlation-Id: <onyx id>

{ "memberId": "123456789", "legacyMemberId": "123456789", "voidCoverageRecord": "N",
  "clientId": "MBRIDSVC", "clientType": "INT", "requestId": "MBRIDSVC-1791064774829-92478" }
  • memberId and legacyMemberId both carry the normalised ID: the MMI spec's advice to improve the hit rate, and exactly the converted-member case (an EMR still holding the pre-conversion ID).
  • No dosStartDate/dosEndDate: the full history is evaluated locally so INACTIVE can say why and show the nearest dates. No searchMode. No demographics ever.
  • requestId follows MMI's convention, new per call, logged with the correlation id and returned to Onyx as mmiRequestId.
  • Timeouts: connect 2 s, read 5 s (mmi.connect-timeout / mmi.read-timeout). No retry: MMI averages about 16 ms over millions of calls a month; a 5-second answer is already a problem worth surfacing, and Onyx retries later on a 503.

9.2 What we read

The MMI DTOs declare only memberId, subscriberMemberId, memberDob, legacyMemberId, company, lineOfBusiness, restrictedData, migrationEffectiveDate and coverage[]{effDate, endDate, groupId, voidFlag}, plus the envelope's messages[]. Names, SSN, gender, PCP, group name, MBI and agency numbers are discarded during deserialization and cannot be logged or returned by accident. Dates are MM/dd/yyyy, parsed strictly; endDate null, blank or 12/31/9999 means open-ended.

9.4 The stub

For developer runs and tests an in-process stub answers from mmi-stub/members.json with MMI's documented behaviour: exact match, 9-digit match returning the family, legacy-id match and the second pass through legacyMemberId. Reserved IDs simulate faults (500, timeout, 400, error message with and without members, unreadable body, a record without an id, a member whose only span is unreadable). Two guards keep canned answers out of PQA and PROD: the stub refuses to start with any explicitly active profile other than dev or test, and it refuses to start inside a Kubernetes/OpenShift pod at all (KUBERNETES_SERVICE_HOST). Because the default profile is dev (so STS runs with one click), every deployment must set SPRING_PROFILES_ACTIVE; a pod that forgets it fails at startup instead of answering from fixtures.

10Selecting the member

From the records MMI returned to the one that represents the patient on the date of service. MMI's record order is never a criterion, and nobody is ever picked "by default".

  1. Merge duplicates. Two records with the same company and the same stored ID (compared without whitespace, case-insensitively) become one, with their spans combined. A warning is logged.
  2. Link converted pairs. Records linked through legacyMemberId in either direction (A's legacy id is B's id, or the reverse, transitively) are one person with several records. This is how a THP↔HPHC conversion comes back from MMI's second pass.
  3. Apply the date of birth, when sent. If at least one record carries a DOB, keep only persons with a matching DOB. None left → 422 DOB_MISMATCH, including when a single record came back (an EMR that appended 01 to a dependent's card number is caught here). If no record carries a DOB at all, continue unverified with a warning: a request with a DOB is never worse off than one without.
  4. Count persons. One → step 5. Several → AMBIGUOUS with one candidate per person (the record covering the date, else the most recent), sorted by company then ID; ambiguity.reason is DOB_NOT_DISCRIMINATING when a DOB was applied (twins), else MULTIPLE_PERSONS.
  5. Pick the record within the person. One record: that one. Several (a converted member): the record whose coverage covers the date of service; if both do, the newer record (the one naming the other as its legacy id); if neither does, the record whose coverage ends last. The coverage reason and the nearest dates are then computed over all of the person's spans, so a gap between the old and the new record is reported as a gap with both dates. The vendor format follows the picked record's company: a member converted to HPHC gets the HPHC ID for a post-migration date and the THP ID for a pre-migration date.

TMP and SCO have no dependents, so a 9-digit card number always yields one person and resolves directly; no DOB is needed. Only Together and HPHC commercial families can reach AMBIGUOUS.

11Coverage status

Evaluated on the selected record's readable, non-void spans. lineOfBusiness, restrictedData and groupId take no part in the decision.

  1. Covers: a span covers the date iff effDate ≤ date ≤ endDate, both inclusive; endDate null, blank or 12/31/9999 is open-ended.
  2. ACTIVE iff at least one span covers the date. The reported span is the covering span with the latest start (then the latest end).
  3. INACTIVE otherwise, with exactly one reason: NO_COVERAGE_RECORDS (no readable, non-void spans), NOT_YET_EFFECTIVE (date before the earliest start, with nextEffectiveDate), COVERAGE_ENDED (date after the latest end, with lastEndDate), COVERAGE_GAP (between spans, with both).
  4. Calendar dates only, no time zones. A future date against an open-ended span is ACTIVE; against a known future termination it is COVERAGE_ENDED. A retro-termination that ended coverage after the date of service but before today is still ACTIVE on that date.
  5. Unreadable spans are skipped (bad date text, end before start) with a warning that names the record (masked) and the shape of the bad value. The remaining spans decide. If the member has unreadable spans and no readable one, the answer is 502 UNREADABLE_COVERAGE: a confident INACTIVE on data the service could not read would block care.
  6. Nearest dates always. lastEndDate (end of the latest span before the date) and nextEffectiveDate (start of the earliest span after it) are reported whenever such spans exist, ACTIVE included, so a defaulted date of service still shows recent past and future coverage.
Rows of the evaluator test (today = 2026-10-03)

12Vendor mapping

Four format styles are code; the vendors are a YAML map in application.yaml. No table anywhere else. A vendor change is a YAML edit and a deployment; a new output shape is one enum constant, one switch case and one test row.

public enum VendorIdFormat {
    AS_STORED,     // exactly as MMI stores it            123456789   01
    COMPACT_11,    // 9 digits + suffix, no spaces        12345678901
    SPACED_14,     // 9 digits + 3 spaces + suffix        123456789   01
    SPLIT          // two fields: 9 digits and suffix     "123456789" + "01" (and the 11-character join)
}

A format is applied only when the stored ID has the TMP/SCO shape, 9 digits, one or more spaces, 2 digits (^(\d{9})\s+(\d{2})$). A continuous 11-character Public Plans ID or an HPHC ID does not match and is passed through verbatim for every vendor, so MHK's 14-character format can never turn 34567890101 into something else.

14Running it: resilience, security boundary, PHI, logging

  • Resilience is timeouts and clear statuses, nothing more. Connect 2 s, read 5 s; a failure is a 503 or 502 within seconds; Onyx retries later. No retry, no circuit breaker, no bulkhead, no degraded mode: MMI is a core service, outages are short, and each of those mechanisms is code that must be tested, configured and explained to Onyx.
  • If this service is down, Onyx passes the EMR's member ID through to the vendor as received (owner's rule). Nothing to build here beyond keeping the service boring: stateless, two replicas, graceful shutdown.
  • Security is outside this code. Azure API Management in front of the service owns authentication, certificates and credentials. The service listens on plain HTTP 9090 inside the network and calls MMI over plain HTTP, as the MMI contract states. Actuator exposes only health and info. Swagger UI and the OpenAPI document are off in prod.
  • PHI minimisation. Request: member ID, date, vendor, optional DOB. Response: identifiers, company, line of business, coverage dates. Never: names, DOB, SSN, MBI, PCP, group names. SSN and names are not even declared on the MMI DTOs. Every request and MMI DTO overrides toString() to the masked form; the exception handler never echoes Jackson or validation messages; MMI message text is never returned.
  • Logging. One INFO line per request: outcome, reason, vendor, shape, masked searched and stored IDs, company, line of business, date, whether defaulted, record count, MMI request id, elapsed time. One INFO line per MMI call. Warnings with a searchable marker for data anomalies (UNREADABLE_SPAN, DUPLICATE_RECORDS_MERGED, COMPANY_INFERRED, DOB_UNAVAILABLE_ON_RECORDS, CONVERTED_OVERLAP, CORRELATION_ID_REPLACED). The console pattern carries the correlation id. A test captures the log during every scenario and asserts no unmasked nine-digit run and no date of birth ever appears.
  • Correlation chain. Onyx transaction id → this service's lines → mmiRequestId → MMI's logs. No PHI needed to follow one transaction.
  • Health. /actuator/health with liveness and readiness groups; MMI is deliberately not part of readiness, so an MMI outage never scales this service to zero.

19Open questions (confirm in PQA)

  1. MMI accepts the 9-digit, 11-digit and 14-character forms of a TMP ID equally (owner's statement); the service sends the compact form. If the 14-character form is required for one of them, the parser's "sent to MMI" column changes.
  2. Exact HTTP status and messages[] shapes MMI uses for no match, invalid request and internal error, to confirm mmi.error-message-types: [ERROR] and that no match is members: null.
  3. HPHC IDs are HP + 9 digits everywhere (member-id.hphc-digit-lengths), and a 9-digit search by the digits of an HPHC ID does not match HPHC records.
  4. For converted members, which record carries migrationEffectiveDate and whether the old company's spans are trimmed (affects only the "both records cover the date" branch).
  5. Whether coverage is null or [] for a member with no spans (both are handled the same way).
  6. Carelon's format (D1); Onyx's DOB availability for dependent populations (D2); INACTIVE and restricted-member handling (D3, D4); whether Onyx reads bodies on non-2xx (D5); the DOS window (D6); the registered MMI clientId (D7).
