6API contract for Onyx

6.1 Operation and headers

One operation, POST /v1/interop/resolve with Content-Type: application/json (owner feedback 29 and 30). It finds the member behind the id the EMR typed, says whether coverage is active on the date of service or on every day of a period of service, and returns the id as stored and in every configured vendor's format, so one call serves a prior authorization whose codes go to several vendors. The earlier /api/v1/member-ids/resolve, /api/v1/member-ids/vendor-map and /api/v1/members/resolution are gone and answer 404 ROUTE_NOT_FOUND. POST because the member ID is PHI and must not appear in URLs or access logs; the operation is a pure read and may be repeated. The service always answers JSON whatever Accept header is sent, and always sets Cache-Control: no-store.

HeaderDirectionRule
X-Correlation-IdinOnyx transaction id, 1–64 characters of [A-Za-z0-9._:-], opaque. Missing or invalid → a UUID is generated (and a warning logged with the rejected length).
X-Correlation-IdoutEcho or generated value. Also in the body of error responses as correlationId; a 200 body does not repeat it.
Retry-After: 10outOn 503 only.

FieldRequiredRules

The 400s this service raises itself are a missing or blank memberId (MEMBER_ID_MISSING), an unusable date of service or date of birth (the date codes of 6.4) and a body that is not JSON for the operation (MALFORMED_JSON; WRONG_JSON_TYPE when the body or a field has the wrong JSON type, for example "patient": "x"). None of them reaches MMI. Everything else is answered. The one other 400 comes from MMI itself: its 400 is forwarded as MEMBER_LOOKUP_REJECTED (6.4).

7What Onyx does with each answer

Onyx calls POST /v1/interop/resolve once per prior authorization: a prior authorization with several codes may go to several vendors, and the one answer gives every vendor's format; Onyx keeps vendorMemberIds[] with the transaction and takes the entry for each vendor. Anything in the request the operation does not need, a vendor included, is ignored; a date that cannot be used is a 400, because the answer is always about the date that was sent.

SignalMeaningOnyx action
200 ACTIVEMember verified; coverage.active = true.Send each vendor its vendorMemberIds entry: the memberId of the entry whose vendor is that vendor, already in the vendor's format (for Optum, the 9-character core). Nothing else from the response goes to the vendor; coverage.coverageId stays with the transaction as the reference to the coverage period behind the decision.
200 INACTIVEMember verified; not covered on that date, or not on every day of the period; message says why (ended, not yet effective, gap, no coverage on record, ends within the period of service).Hold for intake (D3). The vendorMemberIds are still there if the business rule says to submit anyway.
200 NOT_FOUNDMMI has no member for this id: its 404 (or a 200 with no members). sourceMessage carries what MMI said when MMI sent a message (6.3)."Member not found" worklist. If Onyx holds a fuller form of the id (for instance with the suffix), one resend with it.
200 AMBIGUOUSA family behind a 9-character ID; no DOB settled it.One resend with patient.dateOfBirth or the member's full id including the suffix. Otherwise intake picks from candidates[]. Never pick a candidate automatically.
400 / 422Request or identity problem. A 400 MEMBER_LOOKUP_REJECTED is MMI itself rejecting the request, its text in the message. Any other 400 is a missing member id, an unusable date or a body that is not JSON.Never retry. Route by error.code and details[].code (section 6.4).
502 / 503 / 500MMI, or this service, could not answer.Retry later (honour Retry-After); if it persists, park the transaction and alert the service owners. MMI outages are rare and short.
No response at all (connection refused, timeout)This service is down or unreachable.Owner's rule: pass the member ID to the UM vendor exactly as it was received from the EMR. Record the correlation id so the transaction can be reconciled later.

Two rules for every row: Onyx never reformats a member ID itself when the service is up, and Onyx stores the full response with its transaction; it is the system of record for the decision.

8Member ID: passed through to MMI as typed

What arrives in memberId is not this service's business. It is checked for presence only (missing or blank → 400 MEMBER_ID_MISSING) and sent to MMI exactly as the EMR typed it, with only surrounding whitespace removed, in both memberId and legacyMemberId. No separator stripping, no upper-casing, no length cap, no classification. The owner's reasoning: EMRs send 9, 10, 11, 14, 20 or 40 characters, hyphens, whatever; if MMI can find the member it will, so a shape rule here can only reject real ids (a real PQA id was rejected by the earlier parser) and is MMI's job, not this service's.

  "clientId": "INTEROP", "clientType": "INT", "requestId": "INTEROP-1791086059251-93795" }
  • memberId and legacyMemberId both carry the id exactly as received: the MMI spec's advice to improve the hit rate, and exactly the converted-member case (an EMR still holding the pre-conversion ID).
  • No dosStartDate/dosEndDate: the full history is evaluated locally so INACTIVE can say why. No searchMode. No demographics ever.
  • requestId follows MMI's convention, new per call, logged with the correlation id and returned to Onyx as traceId.
  • Timeouts: connect 2 s, read 5 s (mmi.connect-timeout / mmi.read-timeout). No retry: MMI is a core service that answers quickly in normal operation; a 5-second answer is a problem worth surfacing, and Onyx retries later on a 503.

9.2 What we read

The MMI DTOs declare only memberId, subscriberMemberId, memberDob, legacyMemberId, company, lineOfBusiness, restrictedData, migrationEffectiveDate and coverage[]{effDate, endDate, groupId, voidFlag}, plus the envelope's messages[]. Names, SSN, gender, PCP, group name, MBI and agency numbers are discarded during deserialization and cannot be logged or returned by accident. Dates are MM/dd/yyyy, parsed strictly; endDate null, blank or 12/31/9999 means open-ended.

9.3 Interpreting the answer

MMI's contract has four answers: 200 success, 404 member not found, 400 bad request, 500 internal error. This service maps them one to one: on 200 the records decide the outcome; MMI's 404 is 200 NOT_FOUND; MMI's 400 is 400 MEMBER_LOOKUP_REJECTED with MMI's text; MMI's 500 is 503 MEMBER_LOOKUP_UNAVAILABLE. Only an unknown route of this service is a 404 from this service. The mapping is fixed in RestMmiClient and ResolutionService; nothing about it is configurable. MMI's first message is returned to Onyx as sourceMessage on NOT_FOUND, and MMI's message code and text are appended to the 400 and 503 messages when MMI sent them. Any status outside the four is not MMI speaking but a gateway, proxy or container, and the answer says so.

9.4 The stub

For developer runs and tests an in-process stub answers from mmi-stub/members.json with MMI's documented behaviour: exact match, 9-character match returning the family, legacy-id match and the second pass through legacyMemberId. It receives the id exactly as the service got it from Onyx and matches its fixtures ignoring separators and case (anything that is not a letter or digit is ignored), which is the leniency the owner describes for the real MMI; lastSearched() hands tests the id as the stub received it, so they can prove nothing was reshaped on the way. An id that matches no fixture is answered like the real MMI: HTTP 404 with messages: [ { "messageType": "ERROR", "statusCode": "404", "messageCode": "MEMBER_NOT_FOUND", "message": "No member found for the given id (stub)" } ] and no members, so a DEV-profile NOT_FOUND carries that sourceMessage, and the stub's payload log line prints status=404. Reserved ids (recognised by the first 9 characters of that compacted key) simulate the rest of MMI's contract and the data faults: 500500500 MMI's 500 → 503 HTTP_500 (message The member lookup reported an internal error: INTERNAL_ERROR search failed (stub)); 503503503 → 503 READ_TIMEOUT; 400400400 MMI's 400 → 400 MEMBER_LOOKUP_REJECTED / HTTP_400 (message The member lookup rejected the request: INVALID_REQUEST memberId could not be processed (stub)); 888888888 → 502 ERROR_MESSAGE (ES_TIMEOUT, text search backend timed out (stub)); 202202202 → 502 UNPARSEABLE_BODY; 887777777 → 200 with a warning (an error message beside a member); 886666666 → 502 NO_MEMBER_ID; 880000000 → 502 UNREADABLE_COVERAGE. In Postman the stub's "today" is the real date. Two guards keep canned answers out of PQA and PRD: the stub refuses to start with any explicitly active profile other than DEV or test, and it refuses to start inside a Kubernetes/OpenShift pod at all (KUBERNETES_SERVICE_HOST). The default profile is PQA (so STS talks to the PQA MMI with one click), so every deployment must set SPRING_PROFILES_ACTIVE to its own environment: a pod that forgets it would call the PQA MMI, and a pod started with DEV fails at startup instead of answering from fixtures.
