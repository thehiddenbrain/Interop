Member ID Resolution Service

A small, stateless Spring Boot service for Onyx. It takes the member ID exactly as the provider's EMR supplied it, verifies it with the Master Member Index (MMI), returns the ID as stored and in the format the UM vendor expects (one vendor when Onyx names it, every vendor at once when it does not), and says with one flag whether coverage is active on the date of service.

1Summary

Every UM vendor stores our member ID in its own shape. A THP Medicare (TMP) or SCO card prints 9 characters; our systems store those 9 characters, three spaces and the suffix 01 (14 characters); eviCore, Evolent and Carelon keep 11 characters without the spaces, MHK keeps all 14, Optum receives the 9 characters and the suffix as two separate fields. EMRs type whatever is on the card. Today the mismatch surfaces at the vendor. This service moves the check to the front of the flow: one call from Onyx, one call to MMI, and back come the ID as received, the ID as stored, the ID in the vendor's format and the coverage flag. Two operations share that one lookup: /resolve when Onyx knows the vendor, /vendor-map when it does not yet and wants the id in every vendor's format at once.

Four business answers (HTTP 200)

ACTIVE INACTIVE NOT_FOUND AMBIGUOUS
Onyx branches on outcome; coverage.active is the yes/no flag; message says the answer in one sentence.

Three Onyx branches

200: act on outcome. 400 or 422: never retry, route by code. 502, 503 or no response: retry later; if this service is down, pass the EMR's ID through.

Deliberately plain

No database, no cache, no queue, no retry or circuit-breaker machinery, no security envelope (Azure APIM owns that). About 50 small classes.

Delivered

Gradle project importable into STS, built like your other services (Spring Boot 4.0.7, Gradle 9.5, JDK 17 to 25), in-process MMI stub for developer runs, run scripts, README, Postman collection with tests on every request.

What changed since v0.1, in one paragraph

TMP and SCO members have no dependents, so a 9-character card number resolves directly; the "not confirmed" rule is gone. AMBIGUOUS applies only to populations with dependents (HPHC commercial, Together) when a 9-character ID returns several people and no date of birth settles it. The response is lean: stored replaces "canonical", a boolean coverage.active is the flag, and the legacy, migration, restricted and trace fields are gone. A missing date of service defaults to today and says so. Vendor formats live in application.yaml only (Evolent added, Optum as two fields). Retry and circuit-breaker logic, the API key, the ConfigMap override and the host guard were removed: MMI is reliable, security is external, and a format change is a config edit plus a deploy.

Revised 2026-10-04 (owner feedback 7)

The incoming member id is no longer parsed, classified or capped. It is checked for presence and sent to MMI exactly as the EMR typed it, and the response block is { received, stored, forVendor, forVendorParts }. Section 8 has the rule; the decision log in section 18 lists what was removed.

Revised 2026-10-04 (owner feedback 8)

Onyx does not always know which vendor will receive the authorization when it checks the id. A second operation, POST /api/v1/member-ids/vendor-map, takes the same request (the vendor is not needed) and returns the stored id in every configured vendor's format, vendorMemberIds[], after the same single MMI call. Section 6.6 has the contract; section 7 says when Onyx calls which.

Revised 2026-10-04 (owner feedback 9)

/vendor-map is lenient: only the member id is required. A vendor or any unknown property is accepted and ignored, so the /resolve payload can be sent as is; an unusable date of service or date of birth is ignored, not rejected, and named in a new optional response field, ignoredFields. The only 400s this operation raises itself are a missing member id and a body that is not JSON (MMI's own 400 is forwarded on both operations, section 6.4). /resolve is unchanged and strict. Section 6.6 has the fields; the decision log in section 18 has the entry.

Revised 2026-10-04 (owner feedback 10 and 11)

MMI's contract has four answers: 200 success, 404 member not found, 400 bad request, 500 internal error. This service maps them one to one: on 200 the records decide the outcome; MMI's 404 is 200 NOT_FOUND, whatever the body; MMI's 400 is 400 MMI_BAD_REQUEST with MMI's text; MMI's 500 is 503 MMI_UNAVAILABLE. Only an unknown route of this service is a 404 from this service. Both 200 responses carry a one-sentence message right after outcome, and a NOT_FOUND carries what MMI said in mmiMessage { type, status, code, text } when MMI sent a message; the 400, 503 and 502 error messages carry MMI's code and text. Nothing in the mapping is configurable. Sections 6.3, 6.4, 6.6 and 9.3 have the rules; the decision log in section 18 has the entry.

Revised 2026-10-04 (owner feedback 15)

The response is trimmed to what Onyx acts on: outcome, message, the member id (received, stored, for the vendor or the vendor map), lineOfBusiness (Onyx routes on it), the date evaluated, coverage.active with the covering period, candidates[] when AMBIGUOUS, mmiRequestId and mmiMessage. Removed from the 200 bodies: company, the echoed vendor, coverage.reason, coverage.lastEndDate, coverage.nextEffectiveDate, the ambiguity block and correlationId (the header carries it; error bodies keep it). Why an inactive member is not covered, and what to do about an AMBIGUOUS answer, is said in message. Sections 6.3, 6.6, 7 and 11 are updated; the decision log in section 18 has the entry.

4Scope and non-goals

In scope

  • Two operations over one core: POST /api/v1/member-ids/resolve (the id for the vendor Onyx names) and POST /api/v1/member-ids/vendor-map (the id in every vendor's format, for when Onyx does not yet know the vendor).
  • The member id is sent to MMI exactly as the EMR typed it, whatever its length, separators or case; this service checks only that one was sent.
  • One MMI call per request; TMP/SCO resolve from any form; dependents handled through the DOB or AMBIGUOUS with candidates; converted THP↔HPHC members handled through MMI's legacy link.
  • Coverage flag for the date of service (today when omitted), with the coverage period when active; why an inactive member is not covered is said in the one-sentence message.
  • Vendor formats in application.yaml; a change is a config edit and a deploy.
  • Clear error envelope, masked logging, correlation id, in-process MMI stub for developer runs and tests (profile-guarded and refusing to run inside a pod), profiles with the four MMI URLs.

Non-goals

  • No demographic search of MMI; the ID is the only search key and the DOB never leaves the service.
  • No database, cache, queue, audit store, batch or asynchronous mode.
  • No retry, circuit breaker or degraded mode around MMI (owner: MMI is a core service and is restored quickly when it fails).
  • No authentication, tokens or certificates in this code; the Azure API Management layer in front of it owns security.
  • No pass-through of names, SSN, MBI, PCP, group names, legacy IDs or migration dates. Identifiers and coverage facts only.
  • No coverage over a date range; one date per call.

5How a request flows

Synchronous, on the request thread, no state between requests. Both operations run these steps; steps 5 to 8 are one shared core (ResolutionService.resolveMember), and the two differ only where marked.

  1. Correlation. Read X-Correlation-Id (or generate a UUID); it goes into every log line, the X-Correlation-Id response header and the body of error responses.
  2. Read the JSON. Malformed JSON or a wrong JSON type is a 400 on both operations. An unknown property is a 400 on /resolve and ignored on /vendor-map, whose request type is declared @JsonIgnoreProperties(ignoreUnknown = true).
  3. Validate in one pass. Both operations: member ID present (the only check on it). /resolve, strict: date of service (format, window, default to today), date of birth (format, plausibility), vendor present and well-formed; every problem is returned together as one 400. /vendor-map, lenient: only the member id is required; a vendor is accepted and ignored, an unusable date of service is ignored (today is evaluated, dateOfServiceDefaulted is true) and an unusable date of birth is ignored (it takes no part in the selection), each named in ignoredFields. No MMI call for an invalid request.
  4. Look up the vendor (/resolve only) by code or alias, case-insensitively → 400 UNKNOWN_VENDOR with the known codes.
  5. Call MMI once with the member id exactly as received, surrounding whitespace removed (section 8), in both memberId and legacyMemberId, voidCoverageRecord = N, our clientId, a fresh requestId (section 9).
  6. Interpret the answer (section 9.3). MMI's HTTP 404 means "no member for this id": 200 NOT_FOUND, and what MMI said goes into mmiMessage. A 200 with no members is NOT_FOUND too, unless it carries an error-typed message (for example ES_TIMEOUT), which is a 502 forwarding MMI's code and text. MMI's 400 has already become a 400 MMI_BAD_REQUEST and its 500 a 503 MMI_UNAVAILABLE in the client, both carrying MMI's code and text. Otherwise map each record, keeping only readable, non-void coverage spans. A member with unreadable spans and no readable one is a 502, never a confident INACTIVE.
  7. Select the member (section 10): merge duplicates, join converted pairs, apply the DOB, one person or AMBIGUOUS.
  8. Evaluate coverage on the date of service (section 11).
  9. Format the stored ID (section 12), never the input: for the named vendor on /resolve; for every configured vendor on /vendor-map, one vendorMemberIds entry per vendor, sorted by code.
  10. Respond with the outcome and its one-sentence message (on NOT_FOUND also mmiMessage), and write one INFO line with masked IDs, outcome, vendor (ALL(5) on the vendor map), timings and the MMI request id.
